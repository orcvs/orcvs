# Specify the Orcvs evaluation machine

Orcvs evaluates every Expression on a stack machine, and this decision names that machine and states what it guarantees. An Expression parses to a flat sequence of at most `EXP_LEN` Atoms in prefix order, where the root Function comes first and its operands follow. The Evaluator walks that sequence from last Atom to first. A literal Atom pushes one value onto the Operand Stack. A Function pops the operands its signature declares and pushes one value in their place. The right-to-left walk is not an implementation preference: it is what makes a Function's operands reach it in signature order, so reversing it would silently transpose every operand of every non-commutative Function.

The machine has no memory of its own. Its Operand Stack is created for one Expression and discarded when that Expression answers, so nothing carries from one Expression to the next or from one Tick to the next. ADR 0003 already makes the Source Snapshot the complete language state, and this decision keeps the Evaluator consistent with it: there are no registers, no heap, no persistent variables, and no program counter spanning Expressions. Orcvs is therefore not a virtual machine and should not be described as one. It has no bytecode, because the Atom sequence is re-derived from character Source on every Tick rather than compiled, and it has no control flow, because activation and Portals are Source-resident behaviour rather than machine instructions. The accurate term is a stack-based expression evaluator whose memory is the Source.

The instruction set is one specification, declared in one place. Most of it already is: `define_functions!` is that one canonical table, and the `Function` enum, `ALL`, every spelling, every kind, every signature, and the parser's `TryFrom<&str>` are all generated from it, under a compile-time assertion on spelling width and a denied `unreachable_patterns` that turns two definitions sharing a spelling into a compile error. Each operand's role and position are declared there too, beside its type, and a Function body destructures the operands it was handed rather than indexing them, so an operand order exists in one place and transposing Raw Play's channel and velocity is an edit to the table rather than a silent edit inside a body. An operand's declared type is also its domain where the domain is narrower than the token the parser reads: a MIDI channel and a Play velocity are each read from two Cells as a Number and each convert to a type of their own during extraction, so a Function body holds no validation call and a new MIDI terminal Function inherits its domains from its declaration rather than from a body that remembers to ask for them. Two extraction paths do exist where the language describes one rule with one exception, but that is the exception rather than drift: `.^` and `.v` take a numeric value at evaluation instead of the single type their signature declares, which is the idempotence for nested values that ADR 0021 requires. The parser's literal token list, the operand extraction, and each operand's role name are therefore derived from the single declaration rather than restated beside it. The evaluation dispatch is not: it is still a hand-written match over the Function enum, and whether it should be derived too is a question this decision leaves to be settled separately. This decision fixes that the declaration is single and derived-from; it does not fix its form.

That the declaration is single is also the limit of what can be checked about it. There is no second source for a role name to disagree with, so transposing two complete role declarations within one row cannot fail to compile — in principle, rather than as a limitation of the macro that expands them. A partial transposition, which moves the names and leaves the types, is a type error where the Play Command is constructed. A complete one, which moves each name with its own type, compiles clean, because a struct pattern and a field initialisation shorthand both match by name, so the body is unchanged and every operand still lands in a legal domain. That is the original defect arriving through the declaration instead of through the body, and nothing derived from the declaration can carry it. What carries it is a test per Function whose operand values differ from one another, so that a transposition changes an answer rather than raising a diagnostic: for Raw Play that is the role test, run from Source text as well as from the Operand Stack, and for the non-commutative arithmetic Functions it is the enumerated order test. Nobody should design for a guarantee here that cannot exist.

An instruction answers either a value or an effect, never both and never neither. A Terminal Output Function answers a Play Command and is valid only at the Expression root, as ADR 0016 requires, and the Evaluator never pushes an effect onto the Operand Stack. An Expression that leaves no value answers the absence marker, which is distinct from the empty Sequence that ADR 0007 defines as a value.

Every bound the machine relies on is either proven or diagnosed, and never assumed. The parser bounds an Expression at `EXP_LEN` Atoms and diagnoses a longer one, and `Atoms` carries that capacity in its own type, so a caller who assembles Atoms without going through the parser is held to the same bound. The Operand Stack takes that bound rather than a second number of its own, and the proof is short. No Atom raises the depth by more than one: a literal Atom pushes one value, and a Function pushes one value only after popping the operands its signature declares. A Function of one operand or more therefore has a net change that is never positive, and a nullary Function raises the depth by one exactly as a literal does; neither can raise it by more. Peak depth never exceeds the Atom count, which is already bounded, so a Function of any arity, added later, needs no new proof. Two answers satisfy this decision and one does not. The stack may be proven sufficient for every Expression the parser accepts, with its size derived from `EXP_LEN` rather than written as a separate number, or it may answer a diagnostic when it is exhausted; it does both, because a proof states what is true today and the push would otherwise sit one edit away from panicking. The answer it must not give is a panic, and what makes that unacceptable is where the Evaluator runs. The stack held sixteen slots against the parser's thirty-two before this bound was derived, and a 64-Cell Expression of 32 Atoms — a Raw Play over a chain of fourteen additions — reached a depth of seventeen and panicked inside the push. On the native target that panic unwinds rather than aborting: it leaves the Evaluator inside Tick planning, before any Cell of that Tick is committed, and passes back out through the Source write guard and the Playback lock, both of which recover from poisoning, into the clock task whose handle nothing holds. The process survives, the editor survives, and the Source stays consistent; what stops is Playback, silently and with no diagnostic, which makes the failure harder to trace than an abort rather than milder. On `wasm32-unknown-unknown` there is no unwinding to do, so that same Expression aborts the module and takes the editor with it, and the web shell therefore loses more than the desktop does. It is now a regression test, beside an enumeration of every chain length under every root that pins the deepest walk `EXP_LEN` admits.

Two questions this decision deliberately leaves open. The value model is still ADR 0007's Atom-or-Sequence pair, and ADR 0026 records the uniform alternative in which every value is a Sequence; that choice belongs to the value model rather than to the machine, and it changes how operands are described without changing anything above. The form of the single instruction-set declaration is likewise open: it may be types, or data, or a mixture, and this decision constrains only that there is one of it and that everything else is derived.
