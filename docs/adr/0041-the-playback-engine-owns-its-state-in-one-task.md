# The Playback Engine owns its state in one task

Status: accepted. Refines how [ADR 0002](0002-playback-engine-owns-lifecycle-concurrency.md) is implemented; that decision stands and every guarantee it states is kept. [ADR 0055](0055-playback-diagnostics-are-retained-within-a-bound.md) amends it: the ordered diagnostics are a bounded log shared by the task and its handles, not an unbounded channel.

This decision was accepted as ADR 0040 and renumbered to 0041, so history written before the renumbering — commits, pull requests, and issue files that cannot be rewritten — cites it as "ADR 0040" and means this file rather than [ADR 0040](0040-the-console-paints-from-a-value.md), which held the number first and kept it.

The Playback Engine's state lives in one task that owns it, reached through a cloneable handle that sends messages. It is not shared behind a lock. That task also owns its clock: rather than spawning a separate clock task that calls back in, the engine waits on its message channel and its next deadline together, so a Tick is one arm of the loop that processes `stop` and `retune` on the other.

ADR 0002 decided that the Playback Engine owns its clock task, synchronization, cancellation, stale-clock protection and shutdown rather than making callers coordinate them. That decision is unchanged and is the reason for this one: three of those five are mechanisms that exist only because the state is shared with a second task, and owning the state properly deletes them rather than encapsulating them better.

**Cancellation and stale-clock protection both go.** Today a clock task sleeps until a deadline and calls into the engine through a mutex. A `CancellationToken` wakes a retired task out of that sleep so it stops existing, and a `generation` counter makes a Tick from a retired task decline rather than count — two mechanisms, because neither covers the other's case: cancellation cannot reach a task already past its sleep and blocked on the lock, and a generation check cannot stop a sleeping task from waking forever. With one task there is no second party to be stale relative to. A retune recomputes the deadline the loop waits on. `ClockRunGuard`, whose whole job is noticing that the other task died, goes with them.

**Observation is published, not answered.** A handle that sends messages cannot answer a question synchronously, and the console's frame cannot await one — the browser main thread has no blocking receive at all, so a reply channel is not merely slow there but unavailable. The engine therefore publishes: lifecycle state and the selected destination through a `watch`, whose latest value is read without awaiting, and ordered diagnostics through a channel the console drains without blocking. This is what ADR 0002 called atomically observing state while draining diagnostics, with the atomicity now belonging to the channel rather than to a lock.

**`stop` keeps its synchronous guarantee, and needs one shared bit to do it.** ADR 0002 requires that further Ticks are prevented before `stop` returns. Sending a message does not do that: `send` returns once the message is queued, and the task may be mid-Tick. A one-way flag, set by the handle before the message goes and read by the task before it executes each Tick, restores it. That flag is shared state and is admitted deliberately: it carries one fact in one direction and nothing reads it to decide which state the engine is in. "Someone has asked me to stop" and "am I playing" are different facts and are named differently, so that a later reader does not collapse the second into the first and re-admit what this decision removes.

The alternative was to keep the lock and give the shared state better types — a `Run` value holding what a run owns, a `Clock` beside it, an `Output` that cannot hold a note schedule while disconnected. That was the first design considered and it is a real improvement, but it treats the symptom: state behind a lock is opaque to the type system, which is why the invariants have to be written as comments at each mutation site and why a field whose lifetime is a run could outlive one until it was found by review. Ownership is what makes the ordering expressible, and a task is how a shared handle gets an owner.

The cost is a rewrite of the lifecycle rather than a refactor, paid mostly in tests: most of the engine's suite drives it through test-only doors that become messages. That cost is reduced first, by giving the note schedule a module of its own — those tests are about ownership, expiry and delivery order, and they belong to that module rather than to the engine at all.

The Source/Playback seam of [ADR 0001](0001-separate-source-interpretation-from-playback-engine.md) and [ADR 0037](0037-a-late-tick-loses-its-turn.md)'s Tick Grid rule are unchanged. A run still has one fixed Tick period at a time, still executes its first Tick immediately, and still turns output failures and Overruns into diagnostics without rolling back Source writes or stopping later Ticks.

**MIDI publication belongs to MIDI selection, not the shared output seam.** The first implementation added `published_destinations` to `OutputAdapter` so generic construction could take a subscription before moving the adapter into its task. That forced every non-MIDI Playback handle to carry a permanently closed destination channel. MIDI-specific construction now takes that subscription while the adapter is still in hand, then returns the lifecycle handle and a restricted `MidiSelectionHandle` together. Only the MIDI adapter publishes destinations; only the selection handle carries their receiver. The shared output interface handles command delivery and safety reset, and output-only construction creates no destination channel.

**Selection requests are data, not transitions supplied by callers.** The console opens the port on the thread that can open it; what crosses the queue is an already-open connection as an `Install { destination_id, connection }` request on the same ordered queue as lifecycle requests. The task dispatches it and remains the sole owner of the adapter, connection, note schedule, and lifecycle state. Queue acceptance is not a successful installation: a refused delivery remains an ordered Playback diagnostic. Installation still clears scheduled notes and performs the existing safety action when changing connections. Discovery is not published; only the selected destination identity is.

The queue is parameterized by its output-request type: MIDI requests for MIDI construction and the uninhabited `Infallible` type for output-only construction. A private lifecycle sender erases that type from the public Playback handle without introducing another queue. Its constructor-selected dispatcher is fixed for the task's lifetime; messages cannot carry arbitrary functions that mutate Playback. Clock tests instantiate a reply-only request type in their own fixture below the shipped constructors, rather than adding a production probe or retaining queued closures.

The selection handle owns only a weak queue sender and the nonblocking destination subscription. It cannot keep Playback alive or acquire lifecycle control. A running Orcvs carries the selection capability supplied by construction, not its adapter type: native and browser constructors return MIDI selection, while generic output-only construction exposes no selection method. This keeps the browser's frame reads nonblocking without making general Playback speak MIDI.
