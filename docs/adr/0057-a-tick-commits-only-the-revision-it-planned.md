# A Tick commits only the revision it planned

Status: accepted.

**A Tick is planned with no Source lock held, and committed only against the revision it was planned from.** `SourceCommander::execute` takes one revision's planning inputs — the Grid, the Cells in their shared copy-on-write buffer, the shared `Arc<LanguageMap>` and the revision's `RevisionId` — under one short read guard, releases it, and interprets that snapshot. The commit takes the write lock, compares the Source's current `RevisionId` with the one captured beside the snapshot's contents, and writes the plan's Cells only when they are equal. The comparison and the writes happen under that one write guard, so nothing can land between them. [ADR 0003](0003-source-snapshot-is-complete-language-state.md) is what makes this sound: a Tick Plan is a function of one Source Snapshot and the Tick, so planning from a snapshot produces exactly the plan planning in place would.

The reason is the console. Planning is a large share of a Tick, and holding the write lock through it made every revision read, and so every Render Frame, and every keystroke wait for it as well as for the commit. The commit still holds the write lock while it rebuilds the rows the Tick wrote; shortening that is the Language Map's work, not this decision's. The Language Map's shared schedule ([ADR 0032](0032-schedule-tick-execution-by-dependency.md)'s order, held on the Map since `.scratch/source-audit/issues/19`) travels with the `Arc<LanguageMap>` in the snapshot, so planning reads and fills it without the Source.

**Every write mints a `RevisionId`, so a mismatch means an edit landed while the plan was made.** Committing then would write Cells derived from a Source that no longer exists, over an edit the plan never saw. The plan is refused instead, and refused whole: `PlannedTick::commit` hands back the plan only on acceptance, so a refused plan's Cell writes, Play Commands, diagnostics and locks are dropped with it. Nothing downstream of `execute` — Playback's delivery, its note ownership, its diagnostics — ever sees a plan the Source did not accept.

**A refused Tick is planned again at the same absolute Tick.** The Playback Engine advances its Tick counter only after `execute` returns, so a refusal consumes no musical Tick, and because the refused plan published nothing, planning again repeats no effect. The Tick that finally commits is the one that sounds, planned from a revision holding the edit. This is what [`CONTEXT.md`](../../CONTEXT.md)'s Live Editing already promised: an edit affects the next Tick whose Source Snapshot has not yet been taken, and an edit that lands during planning causes the snapshot to be taken again.

**Retries are bounded, and the bound ends in a Tick that cannot be refused.** After three refused attempts (`OPTIMISTIC_TICK_ATTEMPTS`), the Tick is planned and committed under a single write guard. That attempt is always accepted, so under any rate of editing a Tick ends in one committed plan and at most four plannings. What yields is the editor, for one planning: exactly the wait every edit paid on every Tick before this decision. A refusal needs an edit inside a window that lasts a fraction of the Tick period, so a second refusal in a row already means an editor writing faster than a Tick plans. The only writers that fast are block edits and programmatic writes, and they gain nothing from starving the clock. The Tick still pays for their refusals: each refused attempt is a planning it repeats, so under edits that fast a Tick takes longer than it would planned under the lock. `.scratch/source-audit/issues/07`'s profile puts the Tick's p99 under back-to-back edits at 6.6–9.4 ms, against 4.2–7.9 ms locked. The bound is what caps that cost at four plannings. A Tick already executing is never declined: [ADR 0037](0037-a-late-tick-loses-its-turn.md)'s `is_overrun` check runs before `execute`, so a Tick slowed by retries still commits and sounds late, and the cost falls on the Ticks after it, which are declined if the clock reaches them a whole period late.

The alternatives, and why they lose:

- **Merge the plan onto the new revision.** A plan's writes are derived from every Cell its Turns read, and which Cells those were is not recorded, so there is no sound way to decide that an edit did not affect them. Replanning is the merge that is correct by construction.
- **Retry without bound.** A continuous writer would keep `execute` from returning and so stall the Playback task: the Tick in progress never sounds, and every deadline the stall covers is skipped under [ADR 0037](0037-a-late-tick-loses-its-turn.md). Unbounded optimism turns editing into missed beats.
- **Skip the Tick on conflict.** Silently consumes a musical Tick the Source asked for, which is the one outcome the clock exists to prevent.
- **Hold an upgradeable read lock while planning.** Blocks editors for the whole planning window, which is the wait this decision removes, and `std::sync::RwLock` offers no upgrade.

Taking the Cells out costs a reference count, not a copy: the Source holds them in a copy-on-write buffer that a planning snapshot shares, as it shares the Language Map. The Cells are copied — one allocation of the Grid's bytes, 64 KiB on the shipped Grid (ADR 0054) — only when an edit writes while an attempt still holds them, and then once, by that edit, under the write lock. An uncontended Tick copies nothing: its snapshot is dropped before the commit writes, and `orcvs/tests/allocation.rs` holds a Playback Tick to the locked Tick's allocations. Amended by `.scratch/source-audit/issues/08`; as first accepted, every attempt copied the Cell bytes.
