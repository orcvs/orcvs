# The console paints from a value

Status: accepted. Records how the untransformed layer [ADR 0038](0038-the-console-owns-the-source-grid-transform.md) committed the console to is drawn. It does not reopen that decision, and it decides nothing about what a Cell is classified as, which [ADR 0034](0034-execute-against-live-typed-expressions.md) owns.

The console decides what the Cells of the Source Grid it draws look like as a value, and a separate step turns that value into `Shape`s. `Paint::derive(&RenderFrame, &VisiblePositions)` answers a `CellPaint` per drawn Cell — background, border, foreground, two seam colours and the character shown — and takes nothing else: no `Orcvs`, no `egui::Context`. `SourceShapes::new` then takes that `Paint` together with a `GridViewport`, a `GlyphTable`, the scale and the device scale, and builds the five ordered groups a Render Frame extends the painter with. `show_source` shrinks to those two calls, one `painter.extend`, and the click it answers.

**The Paint covers the Positions the console draws, not every Position the Source holds.** `GridViewport::visible_positions` answers the range and `show_source` hands it straight to the derivation, so the per-Cell call to `cell_visuals`, the `Vec<CellPaint>` that holds its answers, the coalescing fold and the Shape construction all follow the viewport rather than the Source — which is what [ADR 0038](0038-the-console-owns-the-source-grid-transform.md)'s untransformed layer has to do to stay usable at the Grid sizes resize exists to offer. Everything the derivation reads is local to its own Cell, so a Cursor outside the drawn range still blooms correctly on the Cells inside it, and the cull is a saving rather than a change of answer.

`Paint::cursor()` answers an `Option<Position>` for that reason and for no other. `RenderFrame::derive` still takes one selected Position and calls `Grid::assert_owns` on it, so a Render Frame still marks exactly one Cell; `None` says the viewport does not reach it. The alternative considered was an accessor on `RenderFrame` answering the selected Position directly, which would have kept the answer total. It was refused as `orcvs` API growth bought for something the console does not need: the shape step reads the Cursor only to decide which group one drawn Cell's border belongs in, and a Cursor that is not drawn belongs in neither.

**A `Paint` carries no geometry, and that is the whole of what makes it a value.** No `Rect` appears in it. Where a Cell sits is `GridViewport::cell_rect`'s question and is answered and tested there; a `Rect` in the value layer would make every assertion about a colour re-acquire a viewport, which is the coupling this split exists to remove.

**A `VisiblePositions` crossing into that layer is the same rule kept, not an exception to it.** It is two `Range<usize>` over the Grid's own column and row numbers, already clamped to the Grid; the clip `Rect` they were resolved from is consumed in `grid_viewport` and never arrives. The rule is there so that naming a Cell costs no viewport, and naming an index range costs none — a test says `columns: 3..8, rows: 2..7` and builds nothing. `BackgroundRun` answering `columns: Range<usize>` rather than a rectangle was already this same decision, taken one type down. `Paint::background_runs()` is the one derived thing, and it answers column ranges rather than rectangles for the same reason: the coalescing fold that used to be an inline `Option<(Color32, Rect)>` state machine flushed at two sites is now a named function over Positions, testable with no egui linked in at all.

**The console had no test surface for a colour, and it was not a testing decision that removed it.** [ADR 0038](0038-the-console-owns-the-source-grid-transform.md) records the chain and each link forces the next: zooming the Grid while the chrome stays put rules out `ctx.set_zoom_factor`; zooming only the Grid meant `egui::Scene`; `Scene::show` sets a layer transform; `GraphicLayers::drain` applies it to every shape at end of pass, reaching a `TextShape`'s galley through an `Arc::make_mut` that never elides because epaint's `GalleyCache` holds a clone of everything it hands out. Leaving the transformed layer is the only thing that removes that cost, and leaving it took the thousand `egui::Button`s with it — and every widget id, `Response` and accesskit node with them. That is where the per-Cell test surface went. This ADR does not restate or reopen any of it.

**Restoring those widgets would not have restored the surface either, which is worth recording because it looks like it would.** egui populates no colour onto an accesskit node: `fill_accesskit_node_from_widget_info` sets role, label, value and toggled, and the `background_color` and `foreground_color` fields accesskit 0.24.1 defines are never written. A per-Cell widget could answer which Position is under the pointer — which `grid_viewport.rs` already answers with a division — but not what colour that Cell is. The surface this ADR creates never existed under the widgets, so it is a new seam rather than a restored one.

**Reading the flat `Vec<Shape>` is not the fault this decision corrects.** An earlier draft of the effort spec held that it was. It is not: `egui_kittest` 0.36.1's own shipped regression tests walk `harness.output().shapes` and filter by `Shape::Rect` and `Shape::Text` in code where widgets exist, with neither the `wgpu` nor the `snapshot` feature enabled, and `window_fixed_size_is_outer_size` runs its shape-list assertion unconditionally while its image snapshot sits behind a `cfg`. Upstream treats the shape-list assertion as the test that always runs. What was wrong was locality: the console recovered facts it had already stated — deciding a Shape was a background from `fill.a() > 0 && stroke.width == 0.0`, hit-testing a point against those rectangles to name a colour, and subtracting the panel's own fill with a `retain()` written 266 lines from the code that made it correct. One test still asserts paint order through a console pass on purpose, because order across kinds is observable there and nowhere else.

## Rejected alternatives

**Publish `RenderFrame::derive` so a test can build a Render Frame directly.** `RenderFrame::derive` is `pub(crate)` to `orcvs`, so `Orcvs::render_frame()` is the only way `console` can obtain one, and a test wanting a Render Frame without a running `Orcvs` naturally reaches for publishing it. The repository contract forbids exactly this: no shipped function takes a parameter, or reaches a branch, that only a test populates, and a constructor published for a test is that rule's plainest case. The review that raised the candidate put the answer in one sentence — publishing `RenderFrame::derive` is not the fix; the return value is the seam that already exists. `Orcvs::new` is cheap and allocates no toolkit state, so a test that needs a Render Frame builds an `Orcvs` and asks for one.

**And the return value is not the seam either, which is the half that is easy to get wrong.** Having established that `show_source` should answer rather than take, the obvious next step is to have it answer its `Paint` as well as its click. It does not. Nothing in production would read that `Paint`, and `Paint::derive` is already independently reachable from a test, so returning it would be a test-only seam cut into a shipped return type — the same rule, one layer up. `show_source` answers `Option<Position>` and nothing else; `show_source_scene` answers a `PresentedSource { viewport, clicked }`, and `Console::ui` owns the `select` call. The intermediate `PaintedSource` type an earlier draft carried existed only to carry the `Paint` out, and with that gone it had no fields worth a type.

**Build the backgrounds as one `Shape::Mesh` through `epaint::Mesh::add_colored_rect`.** This is the one facility in epaint that does what the coalescing fold is for, and it is refused rather than passed over — nothing else upstream merges adjacent same-colour rectangles, so the fold is the console's own work by default rather than by choice. A single mesh carrying a quad per Cell (`epaint-0.36.1/src/mesh.rs:231`) would skip per-rect tessellation and feathering entirely, need no coalescing at all to cut vertex count, and tile exactly, because mesh quads have no anti-aliased edge. What it costs is the reason to refuse it: it moves vertex placement and pixel snapping out of epaint and into this crate, and it gives up per-rect anti-aliasing for every background the console draws. The fold keeps both in epaint's hands and is a dozen lines with a test that needs no GPU.

**Assert what a Cell looks like with screenshot tests.** This was never the alternative to deriving a value and nobody proposed it; the refusal is recorded here only so the question is not reopened. `.scratch/console-testing/spec.md` owns that decision and rules out `egui_kittest`'s `wgpu` and `snapshot` features: `snapshot` alone ships no renderer and fails at run time, the pair turns on `eframe/wgpu` and undoes a deliberate pin, `deny.toml` would audit `wgpu` for targets no test runs on, and the resulting tests are platform-sensitive by construction — egui's own `kittest.toml` carries different pixel thresholds per OS because MSAA sample placement, texture filtering and WGSL float evaluation are each implementation-defined per GPU, OS, backend and driver. Two cost figures that appeared in an earlier draft could not be reproduced and are deliberately not repeated here.

## Consequences

Nothing on screen changes. The same colours in the same geometry in the same order: the paint order across the five groups, the run rectangles, the background skip on the Cell filled with the Source's own colour, the seam suppression on the Cursor's Cell, and the glyph fallback are all carried over unaltered, and the parity is asserted rather than asserted-about.

The value layer is where a Cell's appearance is now tested, and the harness cost that shaped the old tests is gone with it: no test asserting what colour a Cell is constructs an `egui::Context`, a `RawInput` or a `CentralPanel`. That was the bar rather than a count, because a count invites satisfying it by merging tests.

`Paint` is stored flat as a `Vec<CellPaint>` beside its `Grid` and indexed through `Grid::index`, deliberately unlike `RenderFrame`'s `Vec<Vec<RenderCell>>`. The two shapes are right for their two access patterns — `at(Position)` here, row-order iteration there — and `RenderFrame` is not flattened to match. The cost is that the two layers agree on row-major order by construction rather than by type, so a test pins that agreement.

A second consumer of the paint decision is now possible without a Render Frame being drawn, which nothing needs today. Such a consumer states which Positions it wants; there is no way to ask for a Paint without saying that.

The cost of drawing a Render Frame follows the viewport. That is a claim about the per-Cell work and the allocations, and it is asserted by counting rather than by timing: `paint.rs` counts the `CellPaint`s a culled derivation builds with no `Context` at all, and `console.rs` counts one stroked Cell rectangle per drawn Position and a shape total that falls with the zoom. No frame time is asserted here, because epaint already discards off-screen shapes at tessellation, so what the cull saves is Cell iteration and Shape construction — which is what is counted. `.scratch/source-paint/issues/09-measure-the-console-paint-path.md` is where a benchmark for the path is filed; none was run for this record, and no figure appears in it.
