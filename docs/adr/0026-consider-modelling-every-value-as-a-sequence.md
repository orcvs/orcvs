# Consider modelling every value as a Sequence

## Status

Conceptual

Orcvs currently carries two runtime value shapes. An Atom is one value and a Sequence is many, and a wrapper type holds whichever a Function produced so the operand stack can carry both. The alternative recorded here removes the distinction: every language value is a Sequence, a scalar is a Sequence of one member, and the wrapper does not exist. Functions take and return Sequences, and the operand stack holds nothing else.

The attraction is that ADR 0007's pervasive behaviour is already stated in these terms. "An Atom is repeated across a Sequence, two equal-length Sequences pair element-wise, and incompatible non-scalar lengths diagnose" is three rules only because a scalar is a different shape; with one shape it is one rule, because repeating a Sequence of one member across a Sequence of many is what pairing already does. Promotion disappears for the same reason: Concatenate promotes an Atom to a singleton, and there would be nothing to promote. Encoding is unaffected, because a Sequence renders as the concatenation of its members' complete encodings with no separators, so a singleton encodes exactly as its member does and the round trip through Source Cells is unchanged. ADR 0025's deferred member type becomes the element type of every value rather than of one value shape among two.

It contradicts ADR 0007 in four places, and each is a language decision rather than a representation detail. Select returns "one Atom with its type and encoding preserved" and would return a singleton Sequence. Replace takes "one replacement Atom" and diagnoses "a Sequence replacement", which becomes a length requirement rather than a type requirement. Range diagnoses "Bang, Function, and Sequence bounds", which likewise becomes a length requirement. And ADR 0007 distinguishes the empty Sequence, which plans no Cell writes, from the absence an Expression leaves when it produces no value, which also plans none; making every value a Sequence puts pressure on that distinction precisely where the two currently agree, so it would have to be restated rather than inherited.

The costs are three. Every scalar allocates, which at one Tick per `(60000/bpm)/4` milliseconds is not a live concern but is unmeasured, and an inline singleton representation would remove it if it ever became one. Operand typing changes from asking which Atom a value is to asking whether it holds exactly one member and what that member is, so every scalar diagnostic gains a length case and shape errors begin to overlap with arity errors. And `Interpretation` restates in Sequence terms, which is a change to the seam `lang` publishes to `orcvs` rather than to an implementation behind it.

Orcvs does not adopt this now because there is nothing yet to measure it against. No Source-parseable Function returns a Sequence, so the scalar path and the Sequence path do not both exist in code, and the duplication the unification would remove is predicted rather than observed. The point to revisit is when the broadcasting Atomic Functions and the structural Sequence Functions have landed: that is the first revision in which both paths are written, the pervasive rules are real code rather than ADR prose, and the choice can be made against a diff instead of an argument.
