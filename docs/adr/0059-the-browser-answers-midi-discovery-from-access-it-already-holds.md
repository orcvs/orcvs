# The browser answers MIDI discovery from access it already holds

Status: accepted. Extends [ADR 0041](0041-the-playback-engine-owns-its-state-in-one-task.md) and [ADR 0022](0022-keep-the-core-crate-free-of-the-ui-toolkit.md) to the browser target: the console opens the port, the Playback Engine's task owns the connection once it is open, and discovery and connect answer the frame that called them.

**The browser requests MIDI access once, keeps the answer, and every discovery and connect reads it synchronously.** The console's `MidiBackend` contract is synchronous: `destinations` and `connect` return to the frame that called them, and the browser main thread has no blocking receive, so neither may wait. Web MIDI grants access only through the Promise `navigator.requestMIDIAccess()` returns. The browser backend asks for it when the backend is built, which is when the console is, and stores the outcome in one place on the main thread when the Promise settles. Enumerating `MIDIAccess.outputs` and calling `MIDIOutput.send` are both synchronous once access is held. Opening a port is not, and is described below.

Until the Promise settles, the request's state is itself the answer:

- **Pending.** Discovery and connect both answer a pending error saying access is awaited. `MidiError::pending` marks it as an answer that can change without the performer doing anything, which no native failure is. The menu shows the message in place of the rows, as it shows any discovery failure.
- **Granted.** Discovery lists the connected outputs in the order the output map iterates them. A port with no name is listed by its id. Connect checks the output is still there and connected, then opens it as described below.
- **Unavailable.** A browser without `requestMIDIAccess`, or one that refuses it, answers an empty destination list rather than an error. This is the silent fallback every target without a MIDI service gives, and the reason is logged to the developer console once. The state is final for the page. Access is not requested again, because a browser that refused once refuses again without asking.

**The Promise's settlement wakes the Panel, and the next frame discovers again.** The console's startup discovery runs in the call that sends the request, so on every page load it finds access pending. When the Promise settles, the answer is stored and the Panel is asked to repaint. Each frame whose last discovery answered pending runs discovery again, synchronously, in that frame. So a granted page lists its outputs and selects the first without a Scan, as the desktop does at launch, and a refusing page clears the pending message and reads `None`. Any other discovery failure is still final until the performer Scans, so a broken service is not asked on every frame.

This keeps the rule [`spec.md`](../../.scratch/midi-port-ownership/spec.md) sets: discovery is a synchronous call a frame makes and reads, never a result published into the menu from outside a frame. The Promise callback writes no menu state. It only stores the access answer and wakes the Panel, and the frame completes the startup discovery the console already asked for.

**The page waits a quarter of a second for the answer before it starts the console.** The web entry point sends the access request and waits for whichever comes first: the answer being stored, or 250 ms. A page whose permission is already granted or blocked is answered from the browser's permission store, well inside that bound, so the console's startup discovery reads the settled answer: a granted page shows its first output selected on its first frame, and a blocked page never shows the pending message. A first visit shows a permission prompt the performer may answer late or never, so the wait cannot be unbounded, or MIDI permission would gate a console that is useful without it. 250 ms is the longest a first visit can be held back without the delay reading as a slower load, and a remembered answer that takes longer only costs this polish: the console starts pending and the wake and retry above catch it up. A browser without `requestMIDIAccess` is answered at once and not waited for.

**Connect returns an owned request, and installs nothing until opening succeeds.** This amends the original [port ownership specification](../../.scratch/midi-port-ownership/spec.md)'s unchanged-interface constraint: the calls remain synchronous, but connect now represents ownership before completion. A connected output can still fail to open, for instance when another application holds the device exclusively. Web MIDI reports that only by rejecting the Promise `MIDIPort.open()` returns; a `send` to a port that is not open starts an implicit open whose failure nothing observes. `MidiBackend::connect` therefore returns a `MidiConnectionRequest`: either an already-open connection or an owned pending operation. Native opening returns the former. The browser returns the latter, whose nonblocking poll observes completion. The selection retains that request between frames instead of repeating connect through pending errors. The Promise's settlement wakes the Panel. A refusal reaches the status line while the installed destination keeps playing and receives no safety action.

**Pending requests and live connections share ownership at page scope.** The browser port lifecycle module counts both against the same output. Dropping a pending request releases its claim; success transfers the claim into the connection. A Scan or replacement choice drops the request before discovery or destination validation, and replacing a Source drops it with the old selection. The backend itself owns no pending operation. `Console::open` builds a new backend before the outgoing Playback task has finished shutting down, so backend-local counts cannot describe ownership of a page-wide port. All browser backends share the page's lifecycle module.

An unfinished browser open remains tracked even when its last request is dropped. If it succeeds with no owners, the module closes it. If another request acquires the output before completion, it shares the same open and prevents closure. Failed openings are reported to each owner and are forgotten once the final claim is released. Closing is asynchronous too: a new claim that arrives during close waits for that close to finish before reopening. These transitions are in the generic lifecycle implementation, not the JavaScript adapter or the fake.

**A connection names its output by id, not by holding a JavaScript value.** `MidiConnection` is `Send` because it crosses into the Playback Engine's task, and a `MIDIOutput` is not. The kept `MIDIAccess` lives in a thread-local on the main thread, and the connection looks its output up there on every send. This needs no `unsafe impl Send`: the browser runs the console and the Playback Engine's task (`spawn_local`) on that one thread. A disconnected output refuses the next send, producing the ordered Playback diagnostic. Playback drops a connection after its safety action; Web MIDI delivers messages sent without a timestamp before close completes. The port stays open while any other pending request or connection still claims it, including across Source replacement. Source replacement continues to rebuild destination selection; this ownership rule does not change which destination a new Source chooses.

**System exclusive is not requested.** Orcvs sends channel messages only, and asking for sysex makes the browser's permission prompt ask for more than the console uses.

**The test seam is below port lifecycle policy.** The browser adapter supplies access, output discovery, send, and asynchronous open/close outcomes. The native fake controls those outcomes and records effects, while the same shipped lifecycle module handles claims, abandonment, completion and final release. Tests drive selection over a running Orcvs and assert exact bytes and safety-action ordering. They also exercise overlapping backends, Source replacement during opening, abandonment followed by late completion, multiple pending owners, disappearance while opening, and reacquisition during close. The fake does not implement a second version of cancellation. The headless browser suite checks that the real discovery and connect return without waiting; hardware delivery still requires a browser and a MIDI device.

## Destination choice

An explicit choice belongs to the destination selection module, even when it names the destination already installed. The Panel forwards row activation rather than inferring intent from a changed installed id. If A is playing while B opens, choosing A drops B's pending request and leaves A's connection and Playback untouched: it neither reinstalls A nor sends a safety action. This keeps cancellation from interrupting the output the performer chose to retain.

Choosing B again while B is pending retains that same request. A repeated choice does not restart acquisition; after opening fails, a fresh choice retries. Pending work and the installed destination remain distinct facts, and the selection module decides how each explicit choice affects them.

While A is installed and B is opening, the Output readout continues to name A and the adjacent status says `Opening B…`, using B's destination name. The status is browser-only: it shows while B's open is pending and, once the browser has opened B, until Playback publishes B as installed. The readout changes to B only once Playback publishes B as installed. If opening fails, A remains displayed and the failure is shown. This separates the destination currently receiving output from the performer's pending choice. A native connect answers with a connection already open, so a native choice shows no `Opening …` status; the readout changes once Playback publishes it, and the selection still records the handed-over choice until then, so choosing it again does not reconnect it and choosing A again is not overtaken by it.

## Consequences

- One description of MIDI selection covers both platforms: discovery and port opening on the main thread, answered to the caller, and an open connection delivered to Playback through `install` in the bounded destination slot.
- `console::console_midi::AVAILABLE` is true for the browser build, so the Panel enables the destination ComboBox, offers Scan, and shows Playback failures beside it. A browser that has no Web MIDI shows the ComboBox with the empty copy rather than a disabled one, because whether a browser has Web MIDI is known only at run time.
- A target that is neither native nor the browser still builds the silent backend, which lists nothing and refuses every connect.
- A human with a browser and a MIDI device still has to confirm audible output. The fake proves the bytes and the lifecycle; it cannot prove that a browser's Web MIDI implementation delivers them.
