# The browser answers MIDI discovery from access it already holds

Status: accepted. Extends [ADR 0041](0041-the-playback-engine-owns-its-state-in-one-task.md) and [ADR 0022](0022-keep-the-core-crate-free-of-the-ui-toolkit.md) to the browser target: the console opens the port, the Playback Engine's task owns the connection once it is open, and discovery and connect answer the frame that called them.

**The browser requests MIDI access once, keeps the answer, and every discovery and connect reads it synchronously.** The console's `MidiBackend` contract is synchronous: `destinations` and `connect` return to the frame that called them, and the browser main thread has no blocking receive, so neither may wait. Web MIDI grants access only through the Promise `navigator.requestMIDIAccess()` returns. The browser backend asks for it when the backend is built, which is when the console is, and stores the outcome in one place on the main thread when the Promise settles. Enumerating `MIDIAccess.outputs` and calling `MIDIOutput.send` are both synchronous once access is held. Opening a port is not, and is described below.

Until the Promise settles, the request's state is itself the answer:

- **Pending.** Discovery and connect both answer a pending error saying access is awaited. `MidiError::pending` marks it as an answer that can change without the performer doing anything, which no native failure is. The menu shows the message in place of the rows, as it shows any discovery failure.
- **Granted.** Discovery lists the connected outputs in the order the output map iterates them. A port with no name is listed by its id. Connect checks the output is still there and connected, then opens it as described below.
- **Unavailable.** A browser without `requestMIDIAccess`, or one that refuses it, answers an empty destination list rather than an error. This is the silent fallback every target without a MIDI service gives, and the reason is logged to the developer console once. The state is final for the page. Access is not requested again, because a browser that refused once refuses again without asking.

**The Promise's settlement wakes the Panel, and the next frame discovers again.** The console's startup discovery runs in the call that sends the request, so on every page load it finds access pending. When the Promise settles, the answer is stored and the Panel is asked to repaint. Each frame whose last discovery answered pending runs discovery again, synchronously, in that frame. So a granted page lists its outputs and selects the first without a Scan, as the desktop does at launch, and a refusing page clears the pending message and reads `None`. Any other discovery failure is still final until the performer Scans, so a broken service is not asked on every frame.

This keeps the rule [`spec.md`](../../.scratch/midi-port-ownership/spec.md) sets: discovery is a synchronous call a frame makes and reads, never a result published into the menu from outside a frame. The Promise callback writes no menu state. It only stores the access answer and wakes the Panel, and the frame completes the startup discovery the console already asked for.

**The page waits a quarter of a second for the answer before it starts the console.** The web entry point sends the access request and waits for whichever comes first: the answer being stored, or 250 ms. A page whose permission is already granted or blocked is answered from the browser's permission store, well inside that bound, so the console's startup discovery reads the settled answer: a granted page shows its first output selected on its first frame, and a blocked page never shows the pending message. A first visit shows a permission prompt the performer may answer late or never, so the wait cannot be unbounded, or MIDI permission would gate a console that is useful without it. 250 ms is the longest a first visit can be held back without the delay reading as a slower load, and a remembered answer that takes longer only costs this polish: the console starts pending and the wake and retry above catch it up. A browser without `requestMIDIAccess` is answered at once and not waited for.

**Connect answers pending while the browser opens the port, and installs nothing until it is open.** A connected output can still fail to open, for instance when another application holds the device exclusively. Web MIDI reports that only by rejecting the Promise `MIDIPort.open()` returns; a `send` to a port that is not open starts an implicit open whose failure nothing observes, and the send itself succeeds. So connect asks the browser to open the port and, until the Promise settles, answers a pending error saying the destination is opening. The selection keeps the destination it is waiting on, and the Promise's settlement wakes the Panel, as the access answer does. Each frame whose last connect answered pending connects to that destination again. Once the port is open, connect hands back a connection and the selection installs it. If the browser refuses, connect answers the refusal once, it reaches the status line, and the destination already installed keeps playing: its connection was never replaced, so it received no safety action. A Scan or a choice of another destination abandons the open, and the backend closes that port once it opens unless a live connection holds it. The opening state lives in a thread-local beside the kept access, for the same reason, and connect still returns to the frame that called it.

**A connection names its output by id, not by holding it.** `MidiConnection` is `Send` because it crosses into the Playback Engine's task, and a `MIDIOutput` is a JavaScript value, which is not. The kept `MIDIAccess` lives in a thread-local on the main thread, and the connection looks its output up there on every send. This needs no `unsafe impl Send`. It is sound because the browser runs the console and the Playback Engine's task (`spawn_local`) on that one thread. An output that disconnects after the connect refuses the next send. The MIDI adapter turns that refusal into the ordered Playback diagnostic it already produces for any refused delivery. The connection exists only once its port is open. The backend counts the live connections naming each output and closes the port when the last one is dropped. Playback drops a connection only after its safety action, and Web MIDI delivers messages sent without a timestamp before a close completes, so the close cannot cut the safety action short. Closing releases the device on platforms that grant it to one application at a time; reselecting the selected output builds its new connection before the old one is dropped, so the port stays open across it.

**System exclusive is not requested.** Orcvs sends channel messages only, and asking for sysex makes the browser's permission prompt ask for more than the console uses.

**The browser logic is tested natively over a fake of what it reads.** `WebMidiBackend` is generic over a small `WebMidiAccess` trait. That trait covers the access state, the output map as id, name and connection state, opening, sending to and closing an output by id. The browser build instantiates it with the thread-local adapter over `web-sys`, and the native test suite instantiates it with a fake. The generic backend is what ships, so the fake reaches no branch production cannot. The tests drive a running Orcvs through the console's `MidiDeviceSelection` and assert exact bytes. The output the console opened receives the Note On. The outgoing output receives the full safety action when the destination changes. A disconnected output's refusal reaches the status line. An output that cannot open leaves the playing destination untouched, one that opens later is installed by the next frame, and an abandoned open is released. The headless browser suite builds the real backend and holds that discovery and connect answer without waiting, whatever the browser's permission policy.

## Consequences

- One description of MIDI selection covers both platforms: discovery and port opening on the main thread, answered to the caller, and an open connection delivered to Playback through `install` on the ordered queue.
- `console::native_midi::AVAILABLE` is true for the browser build, so the Panel enables the destination ComboBox, offers Scan, and shows Playback failures beside it. A browser that has no Web MIDI shows the ComboBox with the empty copy rather than a disabled one, because whether a browser has Web MIDI is known only at run time.
- A target that is neither native nor the browser still builds the silent backend, which lists nothing and refuses every connect.
- A human with a browser and a MIDI device still has to confirm audible output. The fake proves the bytes and the lifecycle; it cannot prove that a browser's Web MIDI implementation delivers them.
