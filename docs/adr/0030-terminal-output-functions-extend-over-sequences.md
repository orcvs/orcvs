# Terminal Output Functions extend over Sequences

The Terminal Output Functions extend pervasively over a Sequence operand under ADR 0007's rules, exactly as the Atomic Functions do. `!> 00 7F :#C4E4` answers one Play Command per element and sounds a chord from one Expression. A scalar operand repeats across every element, equal-length Sequence operands pair element-wise, and incompatible non-scalar lengths diagnose. Pervasion stays a declared property of each Function rather than a property of the Terminal Output family, so a later output Function states its own answer in the same table column.

ADR 0007 grants pervasive extension to the Atomic Functions, which answer values, and says nothing about Functions that answer effects. That silence was read once as a prohibition: the first implementation of pervasive extension declared `!>` and `!~` scalar and recorded in `CONTEXT.md` that the Terminal Output Functions take Atom operands only. No decision supported that sentence. This ADR replaces it, and the reason the silence is not a prohibition is that the two constraints which make a Sequence expensive elsewhere do not reach an effect.

The first constraint is the Source encoding. An ordinary Sequence result becomes Cells, and ADR 0007 requires those Cells to re-parse as ordinary Source content with no privileged literal-Sequence reading; that is what forbids a nested Sequence, whose separator-free encoding cannot be told from a flat one. A Play Command is never encoded. It leaves interpretation through `Interpretation`, reaches the Playback Engine, and is delivered by the output adapter, so it never crosses the Grid and the encoding rule has nothing to say about how many of them one Expression produces.

The second is ADR 0028's rule that an instruction answers either a value or an effect, never both and never neither. Many effects are still effects: the kind of answer does not change with its count, and a Terminal Output Function that emits three Play Commands has answered no value and remains root-only under ADR 0004. The rule bounds what kind of answer an instruction gives, not how much of it.

Order is the one thing that genuinely needs deciding. ADR 0020 orders Tick effects by Source position, and every command a broadcast Expression produces shares one position, so position alone no longer totally orders the Tick Plan. Within one Expression, commands are ordered by element index; between Expressions, ADR 0020's Source-position order is unchanged. Element order is the only order the Source can read, because the Sequence's own order is what the operand spells out, and it is the order the Cells would have if the same notes were written as separate Expressions left to right.

Validation and failure follow the Atomic Functions rather than softening for output. Each element validates its own MIDI domains through the operand declaration, and ADR 0016's rule that a mistyped or out-of-range operand emits no MIDI output composes with issue 02's all-or-nothing assembly: a fault at any element diagnoses the complete operation and emits nothing at all, rather than sounding the elements that validated. A partly sounded chord would be worse than a silent one, because the Source could not tell it from a chord that was written that way.

Two Functions in the family need their own answer because they own state across Ticks. Timed Play `!~` schedules one Note Off per element, each at its own element's length, since ownership is already keyed by channel and note. Monophonic Play `!%` owns at most one voice per channel, so a Sequence through it does not sound a chord: ADR 0016 already says the last command owns the channel, and the last element is therefore the note left sounding. That is a degenerate rather than a forbidden case, and it needs no separate diagnostic.

This decision changes the seam `lang` publishes to `orcvs`. `Interpretation::Play` carries one Play Command and must carry an ordered group of them. That is a real cost and it is the reason to decide this now rather than after the Terminal Output family grows: Control Change, Pitch Bend, and Monophonic Play are unbuilt, and each one written against the single-command seam is another call site to change later.

The alternative was a separate Chord Function. It was refused because it needs a new two-Cell spelling, repeats every MIDI domain check Play already declares, and gives the language two ways to sound notes that must then be kept in step. Pervasive extension gives chords with no new spelling and no second contract. Increment `~+` and Interpolation `~>` remain scalar under ADR 0012 for a reason that does not apply here: their exception is about hidden cross-Tick state per element, not about the count of answers.
