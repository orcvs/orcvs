# Derive the Language Map from character Source

The editable and persisted Source remains a Grid of single-character Cells and is the only stored program state. Orcvs derives one Language Map from each Source revision; it identifies Expressions, roots, Language Units, anchors, and multi-Cell footprints for parsing, interpretation, spatial behavior, Glyph classification, and diagnostics. Both layers use the same Grid Positions, so Orcvs gains an Atom-level semantic view without a second mutable grid or coordinate system. Incomplete and invalid Live Edits remain valid Source content but do not form valid Language Units.

The Language Map partitions each row left to right into non-overlapping complete Language Units. At each Position it recognizes a complete canonical encoding or reports that character as invalid, then resumes after the recognized Footprint or after the one invalid character. A Cell already claimed by one unit cannot participate in another. Thus `***` is Bang `**` followed by one invalid `*`, `<<<` is Self-Banging Function `<<` followed by one invalid `<`, and `^^^^` is two `^^` Self-Banging Functions. Expression construction operates on this partition and never reinterprets overlapping character pairs.

The Language Map is a deep module at the seam between character editing and language behavior. Callers ask it about units, roots, and footprints instead of reconstructing token spans themselves. The existing Expression map, parsed Atoms, Glyph classifications, and diagnostics become implementation details behind that interface.
