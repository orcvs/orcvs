# Convert Numbers and Notes explicitly

This ADR records the target language contract; it does not claim that the disjoint Note encoding or conversion Functions are implemented yet. In that target, every Source encoding identifies exactly one Atom type, and every Function declares a predictable result type. Orcvs does not globally coerce between Number and Note or let a Note operand change another Function's arithmetic domain. This keeps parsing, Language Map classification, Portal round-tripping, Sequence element types, diagnostics, and rendering independent of operand context; Function-specific coercions may be added later only where concrete use demonstrates a clearer developer experience.

The target numeric `.` family contains the paired conversion Functions `.v value` and `.^ value`. `.v` always returns a Number: a Number is unchanged and a Note becomes its underlying MIDI byte. `.^` always returns a Note: a Note is unchanged, a Number from `00` through `7F` becomes the corresponding Note, and a Number from `80` through `FF` diagnoses and produces no result. The conversions extend atom-wise across Sequences; if any element cannot convert, the complete conversion diagnoses and returns no partial Sequence.

The family prefix supplies the semantic namespace, so the directional suffixes do not claim a global meaning. Within `.`, `v` lowers a pitched value to its underlying Number and `^` raises a Number to a pitched Note. Other families may reuse those glyphs for spatial or future musical behavior without ambiguity. The exact disjoint two-Cell Source encoding for Notes remains a separate decision; the overlapping hexadecimal/natural-note spelling is not canonical.
