# Convert Numbers and Notes explicitly

This ADR records the target language contract; it does not claim that the contextual Note encoding or conversion Functions are implemented yet. Every literal occurrence identifies exactly one Atom type after its containing Expression is parsed against the consuming Function's fixed signature. The same two Source characters may therefore denote different Atom types in different typed operand positions: `C4` is Number `C4` where a Function requires a Number and Note `C4` where a Function requires a Note. Source stores literal characters rather than persistent type provenance; a standalone operand literal without typed Expression context is invalid. Orcvs does not globally coerce between Number and Note or let a Note operand change another Function's arithmetic domain.

The target numeric `.` family contains the paired conversion Functions `.v value` and `.^ value`. Conversion Functions are the language's explicit type-directed exception: each accepts either member of the Number/Note pair but always produces its named target type. `.v` always returns a Number: a Number is unchanged and a Note becomes its underlying MIDI byte. `.^` always returns a Note: a Note is unchanged, a Number from `00` through `7F` becomes the corresponding Note, and a Number from `80` through `FF` diagnoses and produces no result. The conversions extend atom-wise across Sequences; if any element cannot convert, the complete conversion diagnoses and returns no partial Sequence.

The family prefix supplies the semantic namespace, so the directional suffixes do not claim a global meaning. Within `.`, `v` lowers a pitched value to its underlying Number and `^` raises a Number to a pitched Note. Other families may reuse those glyphs for spatial or future musical behavior without ambiguity. Notes retain their contextual two-Cell pitch spelling from `C/` through `G9`; the consuming Function signature distinguishes an overlapping hexadecimal spelling from a Note spelling.
