Are movers sequential effects or dataflow?

A train of movers heading west, <<<<, rejects the whole Grid's Tick on every Tick. The cause is two accepted decisions that were never reconciled. ADR 0014 gave movers Orca's rule: a mover enters a Cell only if it is empty right now. ADR 0032 and ADR 0034 then scheduled every Tick from the starting Snapshot, and made any write onto a computation that has already run a scheduling bug. Movers satisfy the first and break the second. This page walks through the defect, how it arose, what the original Orca does, and the two models that would make the rules agree.

The two checks

A move is admitted by two checks, and they read different Grids:

// execution.rs:687 — reads the working Grid, after earlier Turns this Tick
let empty = entered.iter().all(|&cell| self.working.is_empty_at(cell));
// execution.rs:691 — reads Cell ownership from the Snapshot parse
let relationships = self.lookup.written_over(&write);
if relationships.functions().any(|c| c.subtree.filter(|d| *d != index).any(|d| self.states[d].attempted)) {
    return Break(diagnose(node, "spatial output reached an executed computation; Tick effects rejected"));
}

The leader's move empties Cell 3 in the working Grid, but nothing updates the Snapshot's ownership map. The follower passes the first check and fails the second. Break discards the Tick, so the next Tick starts from the same Snapshot and fails the same way.

2. Two kinds of write

ADR 0014 defines both kinds in the same document. They answer different questions, and the code runs both through the same guard.

Overwrite: dataflow

Value results, Sequences, replacements, Jump relays. ADR 0014: an ordinary Language Unit "atomically overwrites the complete two-Cell destination, including occupied Source". Its target is known from the Snapshot, so the scheduler orders it before whatever it covers (ADR 0034: "If Function B outputs over or at Function A, B must execute before A"). Reaching a computation that has already run means the schedule was wrong, and rejecting the Tick is the right guard.

Empty-only: a sequential effect

Movers (^^ vv << >>) and Directional Bang emissions (*^ *v *< *>). ADR 0014: a move "tests only newly entered Cells… An empty destination emits spaces… A blocked or out-of-Grid move writes **". Whether it succeeds depends on who reached the Cells first this Tick, which the Snapshot cannot know. It is refused whenever something is still standing there, so it can never land on a standing Unit.

No ADR records that empty-only writes sit outside ADR 0034's ordering rule. The code made that exception piecemeal: mover contact edges are skipped, emitter contact edges are not, and the executed-computation guard runs on both.

3. How the conflict arose

  1. 2026-08-31ADR 0014 (30370e11) adopts Orca's motion: test the newly entered Cells, move if empty, otherwise **. The implementation of that era read the pre-Tick Snapshot; ADR 0031 later proposed row-major evaluation against working Source, where "empty" would mean "empty when this Turn comes", as in Orca.
  2. 2026-09-06ADR 0032 (1dc6452b) replaces row-major execution with a schedule built from the Snapshot's dependencies, so that a Note written below its MIDI consumer still plays in the same Tick. It supersedes ADR 0014's row-major clauses, but does not say what an empty-destination check means under a dependency schedule.
  3. 2026-09-08ADR 0034 (7c7554d5) adds the guard: "An output reaching an already-executed Function is a bug in the ordering, not a supported case." That holds for overwrites. It was written before movers existed.
  4. 2026-09-11e5155c16 adds the movers. Their bundle covers their own Span, so it needs "two exceptions, both keyed on the declaration": no self-edge, and no executed-computation rejection for the mover's own computation.
  5. 2026-09-113a676bcd: >><< forms a cycle that rejects the Tick. Fixed by skipping mover contact edges to intrinsically active roots, because "a move is admitted only into empty Cells, so a contact never writes".
  6. 2026-09-113d39fde5 adds the Directional Bang Functions and the Advance/Emit bundle declaration. Emitters get no contact-edge exception, which leaves the *><< cycle.
  7. 2026-10-01This branch (0ef9e84b) adds a fourth exception for the emitter pair. It keeps the emitter's other edges, because removing them hits the same stale guard on ^^ above *^.

Each exception was argued in a commit message, and none was recorded in an ADR. Each patched one shape of the conflict and left the rest.

4. What the original Orca does

The Orca results below come from running Orca's unmodified JavaScript core (operator.js, library.js, orca.js at hundredrabbits/Orca 223e45c) headlessly in node. The C port (Orca-c 9df9786, sim.c:216-229) has the same movement code; it was read, not run.

// operator.js:81-90 — the whole movement rule, used by E, W, N and S (library.js)
if (!orca.inBounds(offset.x, offset.y)) { this.explode(); return }
if (orca.glyphAt(offset.x, offset.y) !== '.') { this.explode(); return }
this.erase(); this.x += x; this.y += y; this.replace(this.glyph); this.lock()
  • Order. Each frame, parse() lists operators top-left to bottom-right (orca.js:60-70). operate() runs them in that order against the live grid (orca.js:72-80).
  • Emptiness reads the live grid. glyphAt sees every earlier operator's writes this frame. Orca keeps no frame-start copy and no ownership map.
  • The only guard is the lock. move() locks the Cell it enters, so a moved operator never runs twice in one frame. Nothing in Orca ever aborts a frame. Every conflict ends locally, in * or a no-op.
  • Trains depend on direction. W and N run against the evaluation order: the leader goes first and vacates, and the train moves as a unit. E and S run with it: the follower finds the leader still there and becomes *.
  • Written operators wait a frame. Orca has no emitter. A writer such as X placing an E leaves it unmoved until the next frame, because a written glyph has no operator object this frame.

Orca is a sequential-effects model: effects apply in evaluation order against the mutated grid, and order decides. Orcvs already follows it for >>>>, the odd gap and the even gap. It departs only where the Snapshot guard fires.

7. The decision to record

Write the missing ADR before writing code. It amends ADR 0014, ADR 0032 and ADR 0034, and the questions it has to answer are:

  • Which model do movers and emissions follow? Model 1 matches Orca, matches ADR 0006's existing "Turn order decides who finds the Cells empty", and keeps every Orcvs result that already agrees with Orca. Model 2 makes outcomes independent of direction and Source order, at the cost of Orca parity on west and north trains and the odd gap, and ADR 0006's collision rule would have to be redone.
  • Where does the guard apply? Under either model, ADR 0034's executed-computation rule is about overwrites only. The ADR should say so, and say which ordering edges an empty-only writer still owes: a mover's Bang on contact, and a literal operand it fills.
  • Where is the kind declared? The Advance/Emit bundle already says which writes are empty-only. The scheduler and the executor should both derive their behaviour from that one declaration rather than from exceptions in each.

The codebase-design proposals (type-driven and testable) both implement Model 1 from that declaration. The testable prototype deleted the Snapshot guard on the empty-only path and the emitter's contact edges, and all 684 existing orcvs tests still passed. A property test, "no arrangement of movers and Directional Bang Functions rejects a Tick", fails on main and passes on the prototype.
