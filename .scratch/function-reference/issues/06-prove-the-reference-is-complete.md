# 06 — Prove the reference is complete

**What to build:** A test that fails when a Function exists in the Function table but has no example in the reference, so adding a Function without documenting it breaks the build.

**Blocked by:** 02 — Add the Conversion and Sequence Functions; 03 — Add the Tick Functions; 04 — Add the Jump, Bang and movement Functions; 05 — Add the MIDI output Functions.

**Status:** resolved

- [x] The test reads the Function table and the reference's Language Map, and asserts every Function spelling appears as the root of at least one example.
- [x] Its failure message names the missing Functions.
- [x] Every example Expression in the reference parses without diagnostics (result rows excepted).

## Resolution

`console/src/function_reference.rs`'s test module gains two tests.

`every_function_in_the_table_has_a_worked_example` reads `lang::Function::ALL` —
the table's own enumeration, generated by `define_functions!` beside the `Function` enum itself
(`lang/src/atom.rs`) — and the reference's own `orcvs::source::LanguageMap` (via
`Source::language_map`), and asserts every Function anchors at least one
`LanguageUnitKind::Function` unit somewhere in it. The list is never hand-written: a Function added
to the table without a worked example fails this test rather than a checklist nobody remembered to
update. No public API needed adding: `Function::ALL` and `impl Display for Function`
(`f.write_str(self.spelling())`) already existed and are already public; `Function::spelling` itself
stays `pub(crate)`. The failure message names each missing Function by both spelling and variant
name, e.g. `["!b (PitchBend)"]`.

`every_example_expression_parses_without_a_diagnostic_outside_a_result_row` reads the same
`LanguageMap`, built directly from the checked-in text before any Tick runs, and asserts every
Diagnostic's Span sits wholly inside one of three named, reused areas: `one_tick_result_triples`
(the `expected` table `ticking_the_reference_once_writes_every_result_row_exactly_as_written` used
inline, factored out so both tests share it), `movement_areas`'s Cells that are *not* the anchor of
a `LanguageUnitKind::Function` unit (so a mistyped Function spelling inside a movement area would
still fail this test), and `midi_bang_result_areas`. A written result such as `02` sits at a row
start with no Function before it, so the Parser's greedy two-Cell Function read refuses it and
advances one Cell at a time (ADR 0018), naming every one of its Cells "unknown function" or
"invalid Language Unit character" at the *static* parse stage — never at Tick time, since
`orcvs::source::tick`'s scheduling only ever visits Expressions with a `function_candidate`, and a
bare written result never parses as one (which is also why
`ticking_the_reference_once_writes_every_result_row_exactly_as_written`'s
`plan.diagnostics.is_empty()` was already true and stayed true). The failure message names each
offending Diagnostic's anchor position and text.

### A real defect, not a false positive

The diagnostics test caught a genuine bug in ticket 02's Concatenate example rather than needing an
exclusion invented to explain it away. `:&01:-0203` spelled Concatenate's left operand as a bare
literal `01` against its `AtomOrSequence`-declared slot, which the Parser resolves to `Token::Atom`
for parsing purposes. `Token::Atom::decode` always refuses a literal by design
(`lang/src/expression.rs`): a generic Atom operand "has no literal reading" because nothing in the
declaration says whether it means a Number, a Note, or a Char, so "the only thing that can stand at
the position is a nested Function's typed answer" — the same rule ADR 0007 states for a
Sequence-typed operand, extended to the Atom alternative Concatenate accepts beside it. The
Expression therefore diagnosed ("expected a token") at the static parse stage, and Tick scheduling's
`syntax_valid` carried the same fact forward: `syntax_blocks`
(`orcvs/src/source/tick/execution.rs`) silently withheld Concatenate's own Turn every Tick, with no
Diagnostic of its own, because its operands never changed from the checked-in text `syntax_valid`
had already judged invalid. The checked-in result, `010203`, was a hand-typed placeholder that
happened to already match the right answer — never an actual Tick write — which is exactly what
`ticking_the_reference_once_writes_every_result_row_exactly_as_written` could not catch: it only
reads settled Cells back and never asks whether a Tick wrote them. Verified directly (corrupting the
checked-in result Cell by hand and re-ticking left the corruption standing, confirming the Turn
never ran).

The fix changes only `console/assets/function_reference.orcvs`: `:&01:-0203` becomes
`:&.+0001:-0203`, giving the left operand a nested Function's Atom answer (Add's `01`) instead of a
bare literal. This keeps the exact same worked answer (`010203`) while letting Concatenate's Turn
actually run — re-verified by corrupting the result Cell and re-ticking, which now overwrites it
back to `010203`. `console/src/function_reference.rs`'s module doc gains a "Completeness and
diagnostic-cleanliness are proven, not asserted" section recording this.

### Standalone Bang and other non-Function Language Units

Out of scope by the ticket's own wording ("the ticket only requires Functions from the table"):
`**` (standalone Bang) parses to `Atom::Bang`, not a `lang::Function` variant, so it is not, and
should not be, asked for by `every_function_in_the_table_has_a_worked_example`. A Comment
(`LanguageUnitKind::Comment`) is likewise not a Function. Neither is missing anything the completeness
test is responsible for proving.
