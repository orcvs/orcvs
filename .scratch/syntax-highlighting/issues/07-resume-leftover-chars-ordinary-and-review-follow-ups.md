## Decided: the rule reads the claim, not a Leftover Char (2026-09-19)

The "Leftover Char" framing is dropped. The Language Map needs no new fact, because the Parser's claim already separates the two cases:

- An operand slot's Token is its parent signature's declared expectation. An operand claim with no Atom over written content is an Invalid Operand and draws Diagnostic.
- At every Expression start the Parser seeds `(Token::Function, None)` as the thing to try, not as anything declared. An operand slot only enters that branch when `is_function_next()` holds, so a Function claim with no Atom only arises at an Expression start. It means the Cells spell nothing: nothing was expected and nothing failed.

So there are two rules for a Function claim. A claim with an Atom paints Function on the Function tint. A claim with no Atom paints Ordinary with no tint, the same as an unclaimed Cell. `hi`, a written `07`, a lone `|`, the trailing `<` of `<<<` and the `v` of `value` all paint Ordinary. The half-typed spelling loses its warning, which is intended, since a spelling on its way to valid is not an error. No `lang`, `CONTEXT.md` or ADR change. This reverses `04`'s criterion for a written `07` and a lone `|`, and `04` records that. Inside a Reservation, `06`'s Output Portal paint still takes precedence.

Built in `orcvs::source::LanguageMap::derive_source_paint` (the unbound `Token::Function` arm). It was built in `console/src/style.rs::claim_paint` when this issue resolved; [ADR 0050](../../../docs/adr/0050-the-language-map-answers-source-paint-per-cell.md) moved the decision into the Language Map without changing it, and `claim_paint` and its `style::tests::an_unbound_function_entry_draws_ordinary_with_no_tint` no longer exist. Pinned from written Source by `orcvs::render_frame::tests::a_lone_pipe_and_the_cell_beside_it_are_unclaimed` and `a_written_07_is_two_unclaimed_cells`, and end to end by `paint::tests::text_that_spells_no_function_is_ordinary_while_an_invalid_operand_stays_diagnostic`.

**The `02`/`03` migration found a real defect, which is worth recording apart from the test move.** Three `style.rs` tests asserted `bound(Token::Atom)` and `bound(Token::Sequence)` — claim shapes the Parser can never mint. Two independent reasons in `lang`: `Token::decode` refuses both outright (an Atom operand has no literal reading, a Sequence no literal spelling), and when a nested Function fills such a slot `take_language_unit`'s `is_function_next()` branch records the entry under `Token::Function`, so the declared Token never reaches the Render Frame. Probing `:<:-0104` confirms it carries Function and Number claims and no `Token::Sequence` claim anywhere. The assertions still held for the reachable unbound shape, because `operand_paint` tints identically for Pending, Valid and Invalid — so this was a latent coverage lie rather than a wrong rule, and exactly the failure the criterion's "where a Source can produce them" was hedging against. Fixed at source: those fixtures now use `unbound`, and `unbound()`'s doc carries the reachability rule. All four operand Tokens are reachable; Atom and Sequence only ever arrive `atom: None`.

The hand-built `style.rs` tests were kept rather than replaced, against this ticket's word "instead". They read `claim_paint` arm by arm with no runtime, no `Orcvs`, no Grid and no Reservation geometry to stay clear of, which ADR 0040 argues for directly; the Source-driven tests prove the path reaches those arms. What the unit tests were wrongly carrying was the reachability claim, and that has moved to `paint.rs` where a Source can be written.

Two `04` entries closed as coverage rather than defects: both new tests passed on first run against unmodified code, and were shown non-vacuous by inverting their expectations. Recorded that way rather than as fixes.
