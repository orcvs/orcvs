# 05 — Stop chrome borrowing Source Paint colours

**What to build:** The four egui `Visuals` fields the console borrows from Source Paint — `extreme_bg_color`, `faint_bg_color`, `error_fg_color` and `warn_fg_color` — take chrome colours of their own, so nothing in the chrome depends on the Source scheme.

**Blocked by:** 01 — Decide where Source colour authority lives.

**Status:** ready-for-human

**Tags:** release/v1

## The defect, restated

The original defect was an ordering one: `style()` runs at `console/src/console.rs:800` and the restored settings arrive at `:839`, so `style()` reads `DEFAULT_SOURCE_BACKGROUND` and `DEFAULT_BANG` (`console/src/style.rs:296-299`) and cannot do otherwise. With `persistence` on, a viewer who retunes the Source background and restarts gets a Grid painting the restored colour and chrome still seeded from black.

ADR 0051 makes that the wrong problem. Chrome affordances take chrome keys; Source Tokens take scheme slots. `extreme_bg_color` and `faint_bg_color` are egui's own panel and widget backgrounds, and `error_fg_color` and `warn_fg_color` are affordance colours — the same category as `editorError.foreground`. None of the four is a Token colour, and the borrow is what made them look like one.

So the fix is removal, not seeding. With the borrow gone there is nothing at startup that needs the restored scheme, and the ordering question has nothing left to order.

## Acceptance

- [ ] The four fields take chrome colours, named alongside the console's other presentation tokens rather than read from Source Paint.
- [ ] `style()` no longer reads `DEFAULT_SOURCE_BACKGROUND` or `DEFAULT_BANG`, and does not gain a `Scheme` or settings parameter — it needs neither.
- [ ] `style()`'s doc comment drops the argument about live `Theme → Source colours` edits not reaching these fields. It is answered by their no longer being Source colours.
- [ ] A `persistence` build that stores a non-default Source scheme opens with chrome unchanged, because chrome does not read it. `mise run test_persistence` passes.
- [ ] A build without `persistence` is unchanged, and the existing style tests (`console/src/style.rs:674`, `:685`) still pass, adjusted for the values if they move.
- [ ] The two read sites — `console/src/console.rs:2042` and `:2218`, both `ui.visuals().error_fg_color` — are checked against the chosen chrome error colour rather than assumed to still look right.

## Interaction with 03 and 02

`03` replaces `style()` with `style(theme)` and `install(ctx)`, and `02` removes the `set_theme(Theme::Dark)` beside it. All three edit the same few lines of `Console::new`. This issue changes what `style()` reads, not when it is called or which themes it registers, so it composes with either — but whichever lands second rebases onto the other rather than racing it. No blocking edge is recorded because neither ordering is wrong.
