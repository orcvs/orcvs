# 07 — Load versioned Orcvs Theme files

**What to build:** Discover native Orcvs Theme files at startup and import them on WASM through one versioned document model. Base16 loading is deferred.

**Blocked by:** 03 — Derive the console's chrome from the Theme; 04 — Decide the light built-in Theme; 06 — Paint the Source from a named Theme; 08 — Validate a Theme’s composited contrast; 11 — Validate chrome contrast through the painted composition.

**Status:** resolved

**Tags:** release/v1

- [x] Parse the Orcvs format marker and version, metadata and typed `style` properties into the document type resolved by `06`. Reject absent/unknown format markers and unsupported versions without partial application. Built-ins and resolved custom documents use one rendering type.
- [x] *(Narrowed to TOML: see the 2026-09-24 comment on TOML-only Theme files.)* Decode each document directly with `toml`'s Serde deserializer into one strict, derived Theme document type and its semantic validator. A Theme document is a `.toml` file, its extension matched case-insensitively; `.json`, `.yaml`, `.yml` and every other extension are not Theme files. No configuration framework, layering or environment overlay. Follow `schema.md`'s decoding rules: the root and `style` deny unknown fields, `style` holds one optional field per catalogue property, and each value deserializes into a newtype that validates it. Include quoted colours, numeric widths and explicit optional-fill clearing. Reject duplicate keys, unknown fields and wrong types, with a test for each case `schema.md` lists. Do not implement an Orcvs-specific configuration parser. No Base16 layouts or slot inference are required.
- [x] Malformed input is refused whole and reported, never partly applied.
- [x] Unknown appearance keys and out-of-range widths reject the entire Theme document. The error identifies the offending setting and explains the valid key or range; values are neither silently ignored nor clamped. A failed web reimport preserves the previous valid document. Contrast warnings alone do not reject a document. Tests cover unknown appearance keys, width range boundaries and failed replacement preserving the previous valid web document.
- [x] If the selected native Theme file is missing or malformed, startup succeeds with the default built-in Theme of that appearance and shows an error identifying the Theme and file problem. The saved selection is retained, including across autosave; restoring or fixing the file restores the intended Theme on the next launch. A regression test covers fallback, save, file repair and restart.
- [x] The native target scans `~/.orcvs/themes/` at startup and loads Theme files from that canonical directory. Settings select native Themes by filename stem; a document's `name` is only a display label. No additional XDG or other Theme directory is searched. The WASM target imports a file and uses its filename stem as the Theme identity, with the document name as a display label. Both targets reach the same parser.
- [x] Built-in Theme identities are reserved. A file whose stem collides with one is refused and reported; it never replaces the built-in. Tests cover reserved identities, display-label changes preserving selection, and file renames changing identity.
- [x] Reimporting a file with the same identity on WASM updates the stored document only after successful parsing and validation; malformed input leaves the previous document intact. Test replacement, persistence across restart, filename identity and reserved built-in identities. Contrast warnings alone do not reject an import.
- [x] If multiple native files have the same filename stem, all files with that identity are refused and the conflict is reported with the conflicting filenames. Directory enumeration order never chooses a winner. If the selected identity is conflicted, use the default built-in Theme of the same appearance while retaining the saved selection; resolving the conflict restores the intended Theme on the next launch. Test duplicate identities with both directory enumeration orders, a selected conflicting identity, saved-selection preservation and recovery after conflict resolution.
- [x] On native, Theme files remain authoritative and are read at every startup. Editing a file between runs changes the Theme on the next launch without re-importing it. Application storage never supplies a cached copy of the native file's Theme values.
- [x] During a native session, file edits leave the loaded Theme unchanged until the next launch. This release has no file watching or reload action.
- [x] With `persistence`, settings retain the selected Theme references. On WASM, imported Theme documents are also stored so their values survive restart; without `persistence`, imported documents and selections remain session-only. Native startup file reading is independent of saving selections.
- [x] Resolve the custom document using `06`'s pure inheritance resolver; list it only in the picker matching that parent appearance. No background-lightness inference is needed.
- [x] `08`'s validator runs on load and its report is shown. A Theme that fails the contrast floor is loaded anyway and reported, not refused — the viewer chose it.
- [x] Switching acceptance for a loaded Theme, handed from `04`: a loaded Theme is listed only by the picker of its parent's appearance, selecting it presents it for Source and chrome in the same frame, and its restored selection presents it on the next launch. Extend `console::kittest_tests`' switching tests, which already cover dark and light picker, mode, OS appearance and restored-reference changes against the test-only stand-ins `theme_selection::with_stand_ins` builds, so that they reach the loaded set through `SelectedThemes::new`'s shipped path rather than the stand-ins.
- [x] The window backdrop under a translucent loaded Theme, handed from `04`: eframe's web runner asks `Console::clear_color` after the frame (`eframe` `web/app_runner.rs`), so on the frame a View menu change is applied in it clears to the new appearance's backdrop under the old frame. Neither built-in has a translucent panel, Grid or Cell layer, so nothing shows it today; a loaded Theme can. Either apply a change so the web backdrop and the frame agree, or test that the frame a change is applied in shows no backdrop from the other Theme through a translucent layer.
- [x] *(Accepted as is: see the 2026-09-24 comment.)* A loaded Theme's display label cannot be confused with the View menu's mode radios, handed from `04`'s review: the radios are labelled "Dark" and "Light", so a document named either would share an accessible label with a mode control and make `get_by_label` lookups in `console::kittest_tests` ambiguous. Either distinguish the picker entries from the mode controls or refuse and report such a name, and test a loaded Theme named "Dark".
- [x] `mise run check_wasm` passes.


## Comments

**Why a loader at all, given compiled-in schemes exist.** The point of adopting base16 rather than a shape of our own is the several hundred published schemes. Compiled-in schemes prove the template; the loader is what makes the ecosystem reachable without a release.

**Scheme identity.** Settings reference a Theme rather than storing its resolved values. A built-in Theme resolves from the compiled-in definition. On native, a loaded scheme resolves from its authoritative file, read at startup. On WASM, it resolves from the imported document, retained in storage when persistence is enabled.

**2026-09-21 — native files are authoritative.** The user confirmed: “On startup Orcvs reads the files.” This supersedes the native stored-copy requirement: startup rereads scheme files, rather than restoring their values from application storage. Web documents retain their storage-backed import path. File discovery and in-session reload behaviour remain to be decided.

**2026-09-21 — discovery location confirmed.** The user chose `~/.orcvs/themes/` as the canonical native directory, scanned at startup, with settings selecting Themes by name. There is no second search location or precedence rule. This settles discovery; in-session reload behaviour remains open.

**2026-09-21 — startup fallback confirmed.** For a missing or malformed selected Theme, use the default built-in Theme of the same appearance and show the error. Preserve the saved selection so repairing the file restores that Theme on the next launch. Fallback must not rewrite settings during autosave.

**2026-09-21 — reload and identity confirmed.** Native file edits take effect at startup only for this release. Settings reference the filename stem; a document's declared name is a display label. Built-in identities are reserved so a file cannot replace a built-in Theme. This settles the in-session reload question left open above.

**2026-09-21 — web file imports confirmed.** Replace pasted text with file import. The filename stem is the identity on both targets; reimporting the same filename updates the web document. Browser storage retains imported documents when persistence is enabled.

Contrast warnings alone do not reject a document.

**2026-09-21 — duplicate native identities confirmed.** If multiple native files have the same filename stem, all files with that identity are refused and the conflict is reported with the conflicting filenames. If the selected identity is conflicted, use the default built-in Theme of the same appearance while retaining the saved selection; resolving the conflict restores the intended Theme on the next launch.

**2026-09-21 — published-format correction.** [Upstream examples](https://github.com/tinted-theming/home/blob/main/styling.md#yaml-scheme-examples) include legacy flat slots and modern nested `palette` slots. The earlier flat-only description would not satisfy loading published base16 schemes. Schema preparation is recorded in `../schema-draft.md`; proposed values there are not accepted defaults.

**2026-09-22 — one Orcvs format confirmed.** The user chose one versioned Orcvs Theme format with named style properties. Base16 is inspiration only; importing/conversion is deferred. This supersedes the earlier sixteen-slot, palette/template and published-scheme requirements. Native startup loading, web file imports, exact inheritance, strict validation and the confirmed appearance controls remain in scope.

**2026-09-23 — standard representations confirmed.** TOML is the default representation because it is conventional in Rust projects. JSON and YAML are also accepted by extension. The `config` crate supplies those mature decoders and Serde extraction; Orcvs keeps one typed Theme schema and its semantic validation. Its default features are disabled and only `toml`, `json` and `yaml` are enabled. This supersedes the hand-written bounded YAML subset and its no-new-dependency preparation constraint. `config` is preferred over Figment 0.10.19 because it declares an MSRV below the workspace's and its YAML feature uses maintained `yaml-rust2` instead of deprecated `serde_yaml`.

**2026-09-23 — direct decoding replaces `config`.** A probe of `config` 0.15.26 showed it cannot meet the strict model: its intermediate value layer converts types (`version = "1"` passes as an integer, `'0.5'` as a width, `5` and `true` as strings), accepts duplicate JSON keys with the last value winning, and drops line and column from type errors. The user chose direct decoding with TOML, JSON and YAML all kept. `toml` 1.1.6 and `serde_json` 1.0.151 are already in `Cargo.lock` as transitive dev-dependencies (`egui_kittest`, `wasm-bindgen-test`); shipping them makes them normal `console` dependencies. For YAML, `serde-saphyr` 1.3.0 is chosen: it is actively released, is pure Rust with `#![forbid(unsafe_code)]` in it and its parser `granit-parser`, declares Rust 1.89, has no RustSec advisory, passes the repository's `deny.toml`, compiles for `wasm32-unknown-unknown`, and exposes options to reject merge keys, unknown tags and YAML 1.1 booleans, and to bound aliases. Rejected: `serde_yaml` (deprecated), `serde_yml` (RUSTSEC-2025-0068), and `serde_norway` 0.9.42 (last release December 2024, wraps `unsafe-libyaml`, accepts unknown tags and `.inf`, rejects a leading BOM). One `serde-saphyr` quirk shapes the model: its typed numeric paths parse a quoted scalar as a number, so every scalar is decoded through `deserialize_any`, which respects quoting. The whole model passed a 54-case probe across the three formats; `schema.md` records the cases. This supersedes the `config` entry above; the enabled features are `toml`'s `parse`, `serde` and `std`, and `serde-saphyr`'s `deserialize` alone.

**2026-09-23 — registry, discovery, import and fallback landed; the picker line waits on 04.** `console/src/theme_registry.rs` holds the built-ins, the custom Themes resolved through `decode` and `resolve`, the identities refused with their reasons, and the notices to show. `Console::start`, the shipped entry point, builds it once before the first frame and passes it to `Console::new`. Tests therefore build their own registry and never read the machine's Theme directory. On native, `ThemeRegistry::discover` scans the direct children of `~/.orcvs/themes/`, with the home directory from `std::env::home_dir`. Each file is read to at most one byte past the 1 MiB limit. File symlinks are followed and directory symlinks are skipped. Duplicate stems are grouped before anything loads, so enumeration order decides nothing. On the web, a Theme file dropped on the console is imported. `App::raw_input_hook` takes the dropped files from each `RawInput` once, and files in one drop that share a stem are all refused by name. The `Blob` size is checked, then `DroppedFile::bytes_async` reads the bytes. A valid import replaces the document of the same identity whole, a failed one changes nothing, and each successful import checks the saved selections again. With `persistence`, the imported source documents are stored as JSON under `imported_themes`, within a 2 MiB aggregate budget. An import past the budget stays usable for the session, is not stored, and raises a notice. Each write is compared with the exact string written. A write storage did not keep is reported once and retried only when the imported set changes. An undecodable stored value is moved to `imported_themes_refused` before anything writes the key again. A copy storage did not keep is retried at every store until one is kept, the original stays under `imported_themes` meanwhile, and nothing is written over it; the failure is reported once, sharing the notice with a document write not kept. A stored entry that no longer loads is reported and kept. At startup the saved dark and light identities are resolved. An unavailable one raises a notice naming the Theme and the file problem, and falls back to the slot's default. The saved selection is written back unchanged. `08`'s `validate` runs on every loaded Theme, and any state below the floor goes into a notice; the Theme is never refused for it. The notices appear as a "Theme notices" menu in the top bar and are also sent to `report::error!`.

The fallback, save, repair and restart line is met at the level of resolution and the saved selection. After a repair, the next launch resolves the selected identity to the repaired Theme. The console does not visibly show that Theme yet, because no selection reaches `style::install` or Source painting before `04` activates per-appearance switching. The fallback notice therefore promises only that the selection is kept and the Theme becomes available once its file loads. The light slot's fallback is still `okabe-ito`, the interim shared presentation, and `04` changes it when it accepts `orcvs-light`.

**Remains:** listing each custom Theme in the picker matching its parent's appearance. That line is blocked on `04`, which adds the pickers. The listing should read `ThemeRegistry`'s built-ins and `custom` map, filtered by `Theme::appearance`, and `ThemeRegistry::select` already refuses an identity of the wrong appearance for a slot.

**2026-09-23 — redesign handed from `04`'s review.** The standards review of `theming-04-switching` (PR #129) raised three design findings that belong to this issue rather than a fix-up there, because each shapes how loaded Themes reach the pickers. Settle them with `/codebase-design` when `04` is merged into this branch:

- **One resolver, not two.** `04` adds `console/src/theme_selection.rs`, whose `SelectedThemes::new` passes an `available: Vec<Theme>` to a private `resolved`, and whose `listed` filters that list by appearance for each picker. Shipped builds only ever pass the two built-ins, so the list, the filter and the per-picker loop in `console.rs` exist for this issue, and only the test-only `with_stand_ins` gives an appearance more than one Theme. That parameter sits close to the seam CLAUDE.md forbids. This branch's `ThemeRegistry` already holds the built-ins and the `custom` map and refuses a wrong-appearance identity in `select`. Make `ThemeRegistry` the source `SelectedThemes` resolves and lists from, drop the `Vec<Theme>` parameter, and point `console::kittest_tests`' switching tests at a registry built by the test instead of `with_stand_ins`.
- **One `default_identity`.** Both branches define it: `theme_selection.rs` (dark `okabe-ito`, light `orcvs-light`) and `theme_registry.rs` (`okabe-ito` for both, the interim value this issue expected `04` to replace). Keep `04`'s mapping in one place both modules read. Make it reachable from `persistence.rs` too, which in `04` builds a whole `ThemeSelection::default()` to read one identity back.
- **A Theme identity type.** An identity is a bare `String`/`&str` in `ThemeRegistry::select`, `SelectedThemes::select`, `AppearanceChange::Theme(Appearance, String)`, `ThemeSelection::new(String, String)` and the registry's `custom` and `refused` maps. This issue gives the identity rules (filename stem, reserved built-ins, display label separate), so a small newtype built only from a stem or a built-in constant would hold them in one place. Decide whether it earns its keep before the merge spreads the bare string further.

**2026-09-24 — redesign applied, after merging `04` (PR #129).** All three findings are settled:

- **One resolver.** `SelectedThemes` now owns the `ThemeRegistry` and resolves and lists from it. The `Vec<Theme>` parameter, `resolved`, `with_stand_ins` and the `my_dark`/`my_light` stand-ins are gone. The registry no longer holds a selection: `check_selection` and its fields moved into `SelectedThemes`, which raises one notice per appearance whose selection falls back. Choosing a Theme for one appearance leaves the other appearance's dismissed notice dismissed. A web import goes through `SelectedThemes::import`, which resolves both appearances again, and the console reinstalls the styles in `raw_input_hook`, before the frame that input starts. The switching tests in `console::kittest_tests` start the console with `Console::new` over a registry that has `my-dark.toml` and `my-light.toml` loaded through `ThemeRegistry::import` (`theme_registry::tests_support::with_my_themes`).
- **One `default_identity`.** It is now `ThemeIdentity::default_for` in `theme.rs`: `okabe-ito` for dark and `orcvs-light` for light. The registry's fallback, `SelectedThemes` and `persistence.rs` all read it. The registry's `select` no longer exempts the default identity from the appearance check, so a light selection of `okabe-ito` is reported as a dark Theme and falls back to Orcvs Light.
- **Identity newtype: adopted.** `theme::ThemeIdentity` is built from a file-name stem (`from_stem`, which refuses an empty stem), from a built-in constant, or from a restored selection (`restored`, `persistence` only, which keeps whatever storage held). It also holds `is_reserved`, which `resolve` now uses, so a built-in identity is reserved whichever built-in set a caller passes. `Theme::identity`, `ThemeSelection`, `AppearanceChange::Theme`, both `select` methods and the registry's `custom` and `refused` maps take it.

A selection now reaches painting, so the fallback notice says the built-in "is shown in its place" and that the Theme "is shown once its file loads". The earlier comment's statement that visible restore waits on `04` no longer holds: `console::storage_tests::restored_theme_references_are_presented_or_fall_back_and_save_back_unchanged` saves a fallen-back selection, then launches again with the file loaded and asserts that Source and chrome present it.

The picker line and the switching-acceptance line are ticked. Two lines handed over from `04` remain: the web backdrop under a translucent loaded Theme, and a display label that collides with the mode radios. None of theming/11–15 is touched.

**2026-09-24 — the last two lines.**

- **Backdrop.** The web runner's clear colour is now the backdrop of the Theme the frame it clears under was painted from. `Console::ui` records that Theme's `window.background`, and on `wasm32`, `clear_color` answers from the record (`Console::web_clear_color`) rather than from the style egui passes. By the time the web runner asks, a View menu change in that frame may already have switched the style. Native keeps reading the passed style, because the glow integration asks before it runs the frame. `console::kittest_tests::the_web_backdrop_is_the_theme_its_frame_was_painted_from` chooses Light under a dark OS and checks that the frame it was chosen in has Okabe–Ito's backdrop and the next frame has Orcvs Light's. Before the fix, the call the web runner makes returned Orcvs Light's backdrop on the first of those frames. The browser suite cannot reach the console's private state, so the `wasm32` branch itself is covered by `mise run check_wasm` and clippy for that target, not by a browser test.
- **Label.** Decided by the user: a loaded Theme named "Dark" or "Light", sharing a label with a mode radio, is not a problem. Neither changes: picker entries are not relabelled, and such a name is not refused.

**2026-09-24 — TOML-only Theme files.** JSON and YAML Theme documents are dropped; ADR 0053 records why. A Theme document is a `.toml` file and nothing else, decoded by `toml`'s own Serde deserializer into a derived, strict document type. TOML is typed, always has a table root and refuses repeated keys, so the hand-written `deserialize_any` scalar visitors, the custom `style` map visitor, the root guard and the per-format test matrix are gone with the other two formats. `serde-saphyr` and `serde_json` are removed from `console`. This supersedes the representation parts of the two 2026-09-23 entries above — JSON and YAML accepted by extension, `serde-saphyr` chosen for YAML, and every scalar decoded through `deserialize_any` — and the decoding acceptance line is narrowed to TOML to match.

**2026-09-25 — web import disabled for v1.** `.scratch/menu-structure/issues/04` removed the Theme pickers and the stored selections, and the web reads no settings file, so nothing on the web could select an imported Theme: a dropped file was imported and stored but never presented. The web import is removed rather than left inert: `WebImport`, `ThemeRegistry::import`, the `imported_themes` and `imported_themes_refused` storage keys, `SelectedThemes::import` and the View menu's drop hint are gone, with their tests. The web console has the built-ins alone. Tests that loaded a document through `import` now load it through `theme_registry::tests_support::load`, which takes native discovery's `load` and `add`. Native discovery is unchanged.
