# 06 — Paint the Source from a named Theme

**What to build:** A resolved Theme with named Source and chrome properties, replacing SourcePaintSettings and CursorEffectSettings colours. Built-in definitions, the custom-document model and the pure inheritance resolver belong here. File parsing/loading is `07`, chrome is `03`, and `10` documents and verifies the complete custom-authoring/loading workflow using this resolver.

**Blocked by:** 01 — Decide where Source colour authority lives; paint-cell-cost/04 — Prove Paint recovered without making Source revisions slower; benchmarks/07 — Hold a named benchmark to a recorded floor.

**Status:** resolved

**Tags:** release/v1

- [x] A resolved Theme contains a declared appearance and typed named properties. Built-ins define every value explicitly. Implement the key catalogue and defaults in `../schema.md`; no Base16 Scheme or slot template is required.
- [x] Own pure custom-document resolution here: copy the selected built-in's resolved named values, apply explicit properties, validate parent identity and matching appearance, and preserve optional-fill semantics. - [x] *(Hit-testing test: `13`.)* Source colours, opacity, borders and border widths consume the resolved Theme while preserving Grid structure and input behaviour. Grid background and Cell fills expose colour and opacity. Cell grid lines and Sector Seams each expose independent colour, opacity and width. Cursor, Region and Diagnostic borders expose colour, opacity and width. Widths are bounded; transparent colours can hide lines. Grid line and border widths are measured in display points and retain the same visible thickness as Grid zoom changes; they do not scale with Cell size. Existing square Cells, zoom and spacing remain unchanged. Use the confirmed width bounds and defaults below. Test constant display-point stroke widths and painting/hit-testing consistency at supported zoom levels and display scale factors. Resolve presentation values outside the per-Cell loop and preserve the existing glyph-resource and atlas budgets.
- [x] Grid/Cell border and Sector Seam widths accept finite values from 0 to 1 display point inclusive; chrome border widths accept 0 to 2 points inclusive. Width zero hides the stroke. Fixed display-point widths intentionally replace the previous zoom-scaled stroke behaviour. Test zero, fractional values, inclusive bounds and rejection of nonfinite/out-of-range values.
- [x] Cursor/Region effect width is nominal: retain the existing animated fragment variation of 0.45–1.25 times that width, without Grid zoom scaling. The 1-point maximum constrains nominal width, so an animated fragment can reach 1.25 points. ## Comments

**Why the template is one table.** Ten repeated colour-picker blocks became one `SOURCE_COLOURS` table in `syntax-highlighting/07` for the same reason. The mapping is data; expressing it as ten accessors is what made the previous shape hard to change.

**The contrast rule does not come with this.** `style.rs` currently pins each colour's measured ratio against `#000000` and which side of Comment it reads on. Those are facts about Okabe–Ito, and an arbitrary scheme will break them. `08` replaces them with a validator. Until it lands, keep the existing assertions passing against the Okabe–Ito scheme and do not extend them to the new schemes — asserting a second palette against a first palette's measurements is the thing `08` exists to stop.

**Interaction with `paint-cell-cost`.** That effort exists because `syntax-highlighting/08`–`10` made every drawn Cell about 5.5 times more expensive, and ADR 0052 removed the `slot_written` map from the per-Cell loop: each shared Claim answers whether its slot is written as the Render Frame builds it, and `RenderCell::source_paint` reads that answer with no lookup. `02`'s move of all finished Paint facts onto the Language Map was rejected (ADR 0050); do not rebuild on it. This issue rewrites the same loop. The ordering is recorded as a blocker rather than left to chance: `paint-cell-cost/03` lands first, `benchmarks/07` pins the recovered figure, and this issue is then built against a floor that will fail if resolution creeps back into the per-Cell body.

The two are compatible in kind. ADR 0051 says facts belong to the Frame and the theme maps them to channels, which is the boundary ADR 0052 implements. What must not happen is the mapping itself becoming a per-Cell cost.

Precomputing the role tints remains this ticket's concern: `SourcePaintSettings` does not survive this issue, but the optimisation does, as a precompute per resolved scheme.
