# 25 — Make an operand's token and bind agree at compile time

**What to build:** A decision, then its implementation: the Function table's generated code makes a mismatch between an operand's declared token and its bind a compile error. Today fourteen cooperating macros generate the table (`define_functions!` and thirteen operand helpers, fed by `function_kind!`); a token and bind can disagree and still compile, falling through to an `unreachable!` that only the `#[cfg(test)] declaration_agreement` test catches. The Sequence and Atom-or-Sequence arms of `operand_bind!` bind an empty Sequence instead of failing, which is the same disagreement. The Number/Note conversion Functions declare typed operands but bypass the typed bind, leaving dead generated operand structs under a blanket `allow(dead_code)`, and Portal geometry sits in hand-written `Function::output_portal` and `Function::input_portal` matches outside the table.

**Blocked by:** 05 — Diagnose silent drops in lang; 09 — Move lang test-only API behind cfg(test).

**Status:** resolved

- [x] The chosen approach (fewer macros, a type-level operand description, or another) and its reason are recorded in this ticket. **Decision (maintainer): a type-level operand description.** Each operand type is a Rust type implementing `lang::operand::Operand`, whose `Token: TokenKind` fixes the payload extraction yields and whose `bind` takes exactly that payload. Reason: the type checker enforces agreement rather than macro convention; it removes most of the cooperating macros; whole-value operands (Sequence, AtomOrSequence) bind from the `Value`, so no empty-Sequence fallback exists; and `.^`/`.v` get an honest operand type (`Numeric<Number>`, `Numeric<Note>`: the literal slot is read as one type, and evaluation accepts either numeric type), so they bind through the table.
- [x] A mismatched token and bind fails to compile, shown by a compile_fail doctest.
- [x] No `unreachable!` remains in the generated bind arms, and no operand bind answers an empty Sequence in place of a failure.
- [x] The conversion Functions bind through the table like every other Function, and no dead-code allowance remains for generated operand structs.
- [x] Conversion semantics are preserved when the conversion Functions move into the generated bind. The table declares `.^` with a Number operand and `.v` with a Note operand, but both accept either numeric type today; binding mechanically from the declared type would refuse values ADR 0021's idempotence relies on. Tests show both Functions still accept Numbers and Notes, stay idempotent, broadcast elementwise over Sequences (assembling nothing when any member fails), and report the same diagnostics in the same precedence as today.
- [x] Function-table tests and parser/interpreter property tests pass unchanged. Met for the parser and interpreter property tests and `lang/tests`, which this change does not touch. Not met as written for the Function-table tests, which changed with the design they checked; see the resolution comment.

## Comments

**2026-09-25 — audited against `origin/main` `199c3331`.** Still valid. "About eleven macros" corrected to fourteen. Absorbs 05's former criterion (c), the empty-Sequence bind.

**2026-09-25 — conversion criterion added.** `ConvertToNote` and `ConvertToNumber` are declared `[value: Number]` and `[value: Note]` in `lang/src/atom.rs`, while `Stack::convert` accepts both numeric types. The declaration alone does not describe their accepted inputs, so the move into the table carries an explicit behavioural contract.

**2026-09-26 — resolved in [#164](https://github.com/orcvs/orcvs/pull/164)** (stacked on #159, which is stacked on #156). New public module `lang::operand`: `TokenKind` (the Parser `Token` plus the payload from an Atom or a whole Value) and `Operand` (`Token`, `Bound`, `bind(payload)`). The compile_fail doctest in `lang/src/operand.rs` declares a Note token with a Number bind and fails with `E0053`. Its passing twin differs only in the token, and the error was confirmed by hand, because rustdoc on stable does not check codes. Generated binds take the payload their token yields. They have no `unreachable!` arms, and Sequence and AtomOrSequence bind from the `Value`. Which extraction a Function uses (`Function::binds_whole_values`, now a `const fn`) is carried as the operand struct's `Binding` type, so a body that uses the wrong extraction does not compile. `Stack::convert`, `UnaryOperands`, `ValueOperands`, `check_token`, `Function::domains` and the `cfg(test)` `declaration_agreement` sweep are removed. Rows with no operands generate no struct, so no `allow(dead_code)` remains. Macros left: `define_functions!` (the table's single declaration site), `function_kind!`, `portal_input!`, one per-row `operands!` helper, and the `cfg(test)` `bind_declared!` that drives the table sweep below. Conversion tests were added before the refactor and pass unchanged after it. The Function-table tests did change. The `declaration_agreement` module and its per-row `value_operands_bind_test!` tests are removed, because the type checker now enforces what they swept for at run time; `every_declared_operand_binds_the_lowest_value_its_token_reads` in `lang/src/atom.rs` replaces them as one sweep over every row, binding the lowest value each declared token reads through the row's own extraction. `value_operands_bind_in_signature_order` moved to `lang/src/stack.rs` with the same assertions, and the two stack tests that called `check_token` read the token through `TokenKind::from_atom` instead. The parser and interpreter property tests and `lang/tests` are unchanged and pass. Portal geometry (`output_portal`/`input_portal`) is left out of scope: no criterion covers it.
