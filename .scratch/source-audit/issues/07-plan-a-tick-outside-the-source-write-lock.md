# 07 — Plan a Tick outside the Source write lock

**What to build:** Planning a Tick (scheduling, ordering, interpretation) no longer blocks the console's revision reads; only committing the planned writes takes the Source write lock. Today `SourceCommander::execute` takes the write lock and `Source::execute` plans and commits under that one guard on a Tokio worker. The pieces exist: `plan_tick(&self)` and `commit_tick(&mut self)` are already separate, `RevisionId` names a revision, and `SourceCommander::read_revision` already snapshots the Grid, bytes and an `Arc<LanguageMap>` under a read lock. That snapshot, `SourceRevision`, carries no `RevisionId`, so it cannot by itself validate a commit.

**Blocked by:** None — can start immediately.

**Status:** resolved

Related: 06 shortens the commit's hold on the write lock (the Map rebuild) but is not a prerequisite. 19's schedule cache must be readable from where planning runs, so the two are designed together.

- [x] Capture a consistent Source snapshot under a short read lock, then release all Source locks before planning. The snapshot records the `RevisionId` under the same read guard as the Grid, bytes and Language Map it holds, so the identity commit validates against is the one its contents came from. A planning-only snapshot type distinct from the public `SourceRevision` is acceptable. Revision validation and commit occur together under the write lock; planning does not hold a read guard that blocks editor writes.
- [x] A commit rejects or re-plans when the revision it planned against is no longer current, so an edit made during planning is never overwritten.
- [x] A rejected stale plan publishes no MIDI commands, stale diagnostics, or note-ownership changes. Only the accepted plan reaches Playback delivery.
- [x] Record whether a retry keeps the same Tick and how repeated revision conflicts terminate or yield under continuous editing. Retries cannot duplicate effects or silently consume musical Ticks.
- [x] Deterministic tests place an edit between plan and commit, reject a stale plan carrying MIDI effects, exercise repeated conflicts, and preserve ordering across consecutive accepted Ticks.
- [x] A benchmark or profile measures both revision-read wait and editor-write latency under running Ticks, including contention and retry costs.

## Comments

**2026-09-25 — audited against `origin/main` `199c3331`.** Still valid. The 06 blocker is weakened to a relation: planning can already run on a revision snapshot.

**2026-09-25 — acceptance-criteria review against `199c3331`.** Added stale-plan side-effect and retry contracts. A long-held read lock would still block editing; planning now explicitly uses an unlocked snapshot.

**2026-09-25 — snapshot identity required.** `SourceRevision` (`orcvs/src/source/mod.rs`) holds the Grid, bytes and Language Map but no `RevisionId`; the criterion now requires the planning snapshot to capture its identity consistently with its contents.

**2026-09-25 — schedule cache ownership (from 19, epic PR 8).** The Tick schedule cache lives on the `LanguageMap` (`ScheduleCache`, an `Arc<OnceLock<…>>` shared by every revision holding the same scheduling inputs). A planning snapshot that holds the revision's `Arc<LanguageMap>` already reads and fills it without any Source lock, so this ticket does not need to move it.

**2026-09-25 — implementation (epic PR 9).** Implemented in orcvs/orcvs#154 on branch `perf/plan-outside-lock`, stacked on #153 (`perf/cache-tick-schedule`, itself on #151). The decision is recorded in ADR 0057; `CONTEXT.md`'s Live Editing entry cites it.

- *Snapshot and identity.* `PlanningSnapshot` (`orcvs/src/source/planning.rs`) is internal to `source` and distinct from the public `SourceRevision`. `PlanningSnapshot::capture(&Source)` reads the Grid, a copy of the Cell bytes, the shared `Arc<LanguageMap>` and the `RevisionId` from one `&Source`, which `SourceCommander::planning_snapshot` borrows from one read guard and releases before returning. `SourceRevision` is unchanged. Planning (`PlanningSnapshot::plan`) calls `tick::plan` on the copy and holds no lock; the schedule cache from 19 is read and filled through the `Arc<LanguageMap>` as 19 anticipated.
- *Validated commit.* `PlannedTick::commit(self, &mut Source)` compares the Source's `RevisionId` with the captured one and commits only on equality. `SourceCommander::commit_planned` runs it under one write guard, so validation and commit are atomic with respect to editors. Every Source write mints a `RevisionId` (including a no-write Tick commit), so any edit or commit since the snapshot refuses the plan.
- *Stale effects.* The plan is a private field of `PlannedTick`, reachable only through a successful `commit`; `StalePlan` carries nothing. A refused plan's Cell writes, Play Commands, diagnostics and locks are dropped inside `SourceCommander::execute`, and `PlaybackInner::execute_tick` only ever receives the accepted plan, so delivery, note ownership (`owned.deliver`) and diagnostics see nothing from it. Playback code is unchanged.
- *Retry policy.* A retry keeps the same absolute Tick: the Playback Engine advances its counter only after `execute` returns, and a refused plan published nothing, so replanning neither consumes a musical Tick nor duplicates an effect. `execute` drives a `TickCommit` (`orcvs/src/source/planning.rs`): at most `OPTIMISTIC_TICK_ATTEMPTS = 3` unlocked attempts, then one planned and committed under a single write guard (`execute_locked`, i.e. `Source::execute`), which cannot be refused. So under continuous editing a Tick terminates after at most four plannings, and it is the editor that yields, for one planning — exactly the wait every edit paid on every Tick before. Merge-onto-new-revision, unbounded retry, skip-on-conflict and an upgradeable read lock were rejected (ADR 0057 records why).
- *Tests* (`orcvs/src/source/planning.rs`). `an_edit_between_plan_and_commit_is_never_overwritten` (edit between plan and commit; refused; the edit survives; the same Tick replans from it). `a_refused_plan_carrying_play_commands_delivers_none_of_them` (stale plan carrying a Raw Play C4 is refused, writes nothing, and the replanned Tick sounds nothing). `a_tick_conflicting_on_every_optimistic_attempt_commits_once_under_the_lock` drives the shipped `TickCommit` attempt by attempt (an edit inside each of the three optimistic windows, no guard held between an attempt's plan and its commit, then the locked attempt commits from the edit that landed before it); `a_tick_nothing_edits_commits_on_its_first_optimistic_attempt` pins the first attempt. `a_tick_planned_from_a_snapshot_is_the_tick_planned_under_the_lock` compares snapshot planning with locked planning over three fixtures and four Ticks each. `consecutive_accepted_ticks_apply_in_order_across_refused_plans` (Increment `~+` counts committed Ticks and Clock `~.` names the Tick planned at, across refused plans on alternate Ticks: no double count, no skipped Tick). `a_captured_snapshot_holds_no_source_lock` and `a_snapshot_names_the_revision_its_contents_came_from` pin the snapshot. `ticks_under_continuous_editing_terminate_and_count_once` is the race-sensitive check through the shipped `execute`: 200 Ticks against a concurrent editor all return and count once. Its edits land in a Cell no Tick writes, so edit survival rests on the deterministic tests. The interleavings are built by editing the real Source between `TickCommit`'s private `plan` and `Attempt::commit`, the steps its shipped `run` drives,, as a racing editor does, with no hook, trait or substitute adapter in shipped code. Mutation checks, run by hand and reverted: skipping the revision comparison fails four of the deterministic tests; an attempt budget one smaller or larger, or a refusal left uncounted, fails the conflicting-attempt test; an always-locked first attempt fails the first-attempt test. Making the locked attempt re-plan from a snapshot is not caught deterministically: with no edit in its window it commits identically, and that it holds the write guard throughout is structural.
- *Profile.* `source::planning::tests::profile::profile_revision_reads_and_edits_under_running_ticks`, `#[ignore]`d because it asserts nothing; run with `cargo nextest run --package orcvs --release --no-capture --run-ignored only -E 'test(/source::planning::tests::profile/)'`. A thread executes a Tick every 2 ms over a 128x128 Grid of independent adders (~0.85 ms per Tick) while the test thread reads revisions every 50 µs, then edits paced at 500 µs, then edits back to back. Each is measured with every Tick in the locked mode (`execute_locked`) and through `execute`, in one process. Two runs on an Apple M2 while another agent was building in parallel, so the tails are noisy:

  | measurement | locked p99 | planned p99 | locked p99.9 | planned p99.9 |
  |---|---|---|---|---|
  | revision read | 0.86 ms / 2.2 ms | 0.50 ms / 0.51 ms | 1.2 ms / 77 ms | 0.68 ms / 0.56 ms |
  | paced edit | 0.82 ms / 1.7 ms | 0.57 ms / 0.65 ms | 1.0 ms / 17 ms | 1.5 ms / 2.9 ms |
  | Tick under paced edits (retry cost) | 1.2 ms / 2.7 ms | 2.5 ms / 3.4 ms | 3.0 ms / 4.2 ms | 4.4 ms / 4.6 ms |

  Medians do not move (a read is ~0.3 µs, an edit ~4 µs). What remains of a planned-mode read's tail is the commit: `commit_tick` rebuilds every row the Tick wrote, about half of this fixture's Tick, and that still holds the write lock. Retries cost the Tick's own tail under edits paced this fast; back-to-back edits refuse every optimistic attempt and fall to the locked one (Tick p99 6.6–9.4 ms against 4.2–7.9 ms locked, on 29–36 Ticks). Each attempt also copies the Cell bytes, 64 KiB on the shipped Grid, which `source_whole_grid/snapshot` measures. No CI benchmark is added: a Playback-driven criterion group was tried and discarded because its duty cycle depends on OS timer coalescing (most Ticks overran at 1–3 ms periods on macOS), which the ratio gate would read as noise.
