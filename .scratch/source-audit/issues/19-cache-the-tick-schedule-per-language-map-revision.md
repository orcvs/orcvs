# 19 — Cache the Tick schedule across revisions that change no parse

**What to build:** A Tick re-plans its dependency order only when the parse it depends on changes. Today every Tick rebuilds the whole schedule — `tick::plan` → `schedule` → `computations` → `Lookup::new` → `order_turns`: the per-Expression lookup, the edge set and the topological order — although the schedule depends only on the Grid and the Language Map. The Language Map revision is not a usable key: every committed Tick mints a new `LanguageMapId` and `RevisionId`, even one that writes nothing, and `rebuild_rows` deliberately re-derives rows a Tick rewrote with identical bytes. A cache keyed on the Map revision would miss on every Tick.

**Blocked by:** None. 06 is resolved (orcvs/orcvs#151); the key chosen below compares row derivations and would be correct without row sharing, so 06 was an ordering preference rather than a prerequisite.

**Status:** ready-for-human

Related: 07 moves planning outside the write lock; the cache must be readable wherever planning runs.

- [x] Choose and record a key covering every scheduling input from the Grid and Language Map. It survives both no-write commits and commits that rewrite identical bytes. Merely keeping the revision for no-write commits does not satisfy the latter case; sharing clean rows alone does not cover rewritten rows.
- [x] Define which changes alter scheduling inputs, including Function identity, portal relationships, occupancy and syntax diagnostics. Do not equate unchanged Expression shape with unchanged scheduling inputs.
- [x] A schedule is computed once per key and reused by every Tick planned against it.
- [x] Tests change Function identity, portal relationships, occupancy and syntax between Ticks and compare cached planning with fresh planning, including ordering and scheduling diagnostics. Tests separately prove reuse after no-write and identical-byte-write commits.
- [x] Tick ordering and scheduling diagnostics are unchanged across the existing Tick tests.
- [ ] A benchmark shows Tick planning cost falls for a run whose Ticks write Cells without changing any Expression — "steady state" means that.

A commit that writes any row, identical bytes included, still mints a new Map identity. The key this ticket chooses must still cover the identical-byte case on its own.

**2026-09-25 — implementation (epic PR 8).** Implemented on branch `perf/cache-tick-schedule`, stacked on #151.

- *Key.* The key is the scheduling inputs themselves, compared row by row, not an identity minted per revision. `LanguageMap` holds a `ScheduleCache` (`orcvs/src/source/tick.rs`): an `Arc<OnceLock<Result<Schedule, Vec<Diagnostic>>>>`. `LanguageMap::rebuild` compares every row it re-derived with the same row of the previous revision through `DerivedRow::schedules_as`; when all of them hold the same inputs it clones the previous revision's cache pointer, and otherwise it starts an empty one. `build` and `derive` start an empty one. A no-write commit keeps the whole `Arc<LanguageMap>` (06's decision) and so the cache; an identical-byte rewrite re-derives rows whose inputs compare equal and so shares it; a Tick that writes new values without changing any Expression does too. Carried rows hold their inputs by construction, so the comparison costs O(content of the re-derived rows) per commit and allocates nothing.
- *What alters scheduling inputs.* Exactly what `computations` and `Lookup::new` read from the Map, over the fixed Grid: for each Expression with a leading Function, its Span, its leading Function and anchor, and for every positioned entry its Cells, its parent, and whether it parsed and as which Function; and every Language Unit (kind, anchor, Span; a unit carries no value). Function identity decides Portal access, activation, reservations and so every Portal relationship; Cells decide claims and the row edge diagnostic; parse presence decides syntax blocking; unit anchors and Spans decide a Halt target's occupancy. Portal destinations come from the Function's declaration, never an operand. Operand Literal values, working Source and the Tick are execution's alone. Unchanged Expression shape is not treated as unchanged inputs: a Comment written into Halt's empty target changes no Expression and invalidates the cache. Today an operand that stops parsing also drops its Language Unit, so the unit and parse-presence comparisons co-vary; both are compared because both are read. The doc comments on `ScheduleCache` and `schedule` state the rule that any new read from the Map in scheduling must join `schedules_as`.
- *Computed once per key.* The schedule is ordered lazily by the first Tick planned against the inputs and reused by every later Tick of every revision sharing the cache. `execution::execute` borrows the `Schedule` rather than consuming it; the only per-Tick copy is the schedule's own diagnostics, cloned into the Tick's effects.
- *Ownership, for 07.* The cache lives on the `LanguageMap`, so any holder of an `Arc<LanguageMap>` (the Source, or a planning snapshot taken under a read lock) can plan against it without a lock: `OnceLock` fills it once, from whichever thread plans first. PR 9 needs no change to where the cache lives.
- *Tests* (`orcvs/src/source/tick/schedule_reuse.rs`). Each helper Tick plans through the shared cache and against a freshly ordered schedule from the same Map and asserts equal Tick Plans (writes, Play Commands, diagnostics, locks) and equal Turn order. Invalidation: `changing_a_function_orders_a_new_schedule`, `changing_a_portal_relationship_orders_a_new_schedule`, `changing_occupancy_alone_orders_a_new_schedule`, `changing_operand_syntax_orders_a_new_schedule`, `an_expression_cut_by_the_row_edge_orders_a_new_schedule`; the first four also show that the earlier schedule would plan the edited revision differently. Reuse: `a_commit_that_writes_nothing_keeps_the_schedule`, `rewriting_identical_bytes_keeps_the_schedule` (new Map identity, same cache, already filled), `ticks_that_write_new_values_without_changing_an_expression_keep_the_schedule` (a Clock). Property: `a_shared_schedule_plans_every_tick_as_a_fresh_one_would` over generated revision sequences that rewrite unchanged rows beside edited ones. Mutation check, run by hand and reverted: always sharing fails six of these tests including the property; dropping the unit comparison fails the occupancy test.
- *Existing Tick tests* pass unchanged; two call sites pass `&schedule` to `execute`.
- *Allocation.* `ORCVS_MEMORY_SERIES=1 cargo test -p orcvs --test allocation` block counts are unchanged from 06's (11 empty; 15/29/53 populated); bytes grow by the one pointer the Map holds (e.g. 16x16 populated 4,994 → 5,002). A rebuild that changes scheduling inputs allocates the new cache's `Arc`; one that does not allocates nothing more.
- *Benchmark.* The steady-state series already exist: `source_execute_tick` and `source_execute_tick_edges` rewrite identical bytes every Tick, and `source_execute_tick_portal_inputs` writes a different Increment value every Tick without changing any Expression. Their doc comments now say so. No local run and no speedup is claimed; the comparison is CI's bench workflow on the PR. The last criterion stays open until that comparison is recorded here; resolve the ticket then.
